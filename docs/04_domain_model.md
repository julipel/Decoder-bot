# Доменная модель — MVP персонального AI-ассистента «Декодер»

Документ описывает логическую предметную модель системы: сущности, их жизненные циклы, инварианты, связи и агрегаты. Основан на утверждённых [`docs/01_requirements_analysis.md`](01_requirements_analysis.md), [`docs/02_system_architecture.md`](02_system_architecture.md) и [`docs/03_project_structure.md`](03_project_structure.md) — все поля и правила ниже либо взяты из уже реализованных `domain`-классов (`src/dekoder/modules/*/domain/`, `src/dekoder/shared/domain/`), либо прямо следуют из этих трёх документов. Эти документы не изменялись, структура проекта не менялась, код в рамках этой задачи не менялся.

Это **логическая модель**, а не физическая схема: без ORM, без SQL, без миграций, без API-моделей. Все сущности представлены в терминах dataclass-мышления — набор полей и правил, а не таблиц.

## 1. Сущности

### 1.1 Profile

**Назначение.** Единый профиль автора — стиль изложения и ограничения, которые AI Core применяет к форме ответа (docs/01, §2.3, §4.3).

**Ответственность.** Определяет ФОРМУ и стиль ответа. Не может изменять фактическое содержание, взятое из документов базы знаний (docs/01, §4.2 — прямое ограничение).

**Жизненный цикл.** Создаётся один раз при первом старте приложения из seed-источника (конфигурационный файл/seed-данные), если запись в SQLite отсутствует. В течение работы приложения только читается. Изменяется исключительно вне приложения — прямым обновлением конфигурации или записи в БД (docs/01, §2.3); в MVP нет runtime-сценария редактирования, в том числе через панель администратора.

**Поля:**

| Поле | Тип | Обязательное | Описание |
|---|---|---|---|
| `style` | `str` | да | Стиль изложения и тон ответа |
| `constraints` | `tuple[str, ...]` | нет (по умолчанию пусто) | Ограничения на содержание ответов |

**Инварианты:**
- Существует ровно один экземпляр в системе (docs/01, §2.3 — «один общий профиль на всех пользователей»), не параметризован по пользователю.
- Влияет только на форму ответа, не подменяет фактическое содержание документов (docs/01, §4.2).

Разделение `style` на два самостоятельных поля (`identity` — роль/позиционирование ассистента, `voice` — тон и манера изложения) рассмотрено и не принято — не следует напрямую из docs/01 и не совпадает с фактическим domain-классом. Обоснование — «Замечания архитектора».

**Связи с другими сущностями.** Нет прямых ссылок (ни в одну, ни в другую сторону) — Profile не хранит идентификаторов других сущностей, и ни одна другая сущность не хранит ссылку на Profile (см. также разбор примера ниже, раздел 5).

**Кто имеет право изменять.** В runtime — никто (нет write-операции, кроме первичного посева при пустой БД). Вне приложения — оператор, редактирующий конфигурацию или запись в БД напрямую.

**Use cases:** `SeedProfileIfMissingUseCase` (создаёт при отсутствии); читается `BuildConversationContextUseCase` через `ProfileRepositoryPort.get_profile()`.

### 1.2 DialogueMessage

**Назначение.** Одна реплика диалога — пользователя или ассистента; единица истории диалога (docs/01, §4.4; docs/03, §16).

**Ответственность.** Хранит текст одной реплики. Для реплик пользователя дополнительно хранит статус обработки соответствующего запроса.

**Жизненный цикл:**
1. Создаётся с `role=USER`, `processing_status=RECEIVED` в момент получения сообщения — до начала его обработки.
2. По завершении обработки та же запись переходит в `processing_status=COMPLETED` либо `FAILED` — единственное изменение, которое когда-либо происходит с этой записью.
3. Отдельно, только при успешной обработке, создаётся **новая** запись `role=ASSISTANT` (`processing_status=None`) с текстом ответа. Эта запись после создания не меняется никогда.

Записи не удаляются и не архивируются — в MVP нет такого use case.

**Обязательные поля:** `message_id`, `dialogue_id`, `role`, `text`, `created_at`, `correlation_id`.

**Необязательные поля:** `processing_status` — заполняется только для `role=USER`; для `role=ASSISTANT` всегда `None`.

**Инварианты:**
- `text` обязателен.
- `role` обязательна, одно из `{user, assistant}`.
- `processing_status` существует только у реплик с `role=user`.
- Реплика ассистента создаётся только вслед за реплику пользователя того же запроса (тот же `correlation_id`).
- После создания у реплики пользователя меняется только `processing_status`; `text` и `role` неизменны. Реплика ассистента неизменна полностью.
- Полный текст реплики хранится только здесь и никогда не дублируется в техническом журнале (docs/02, §14).

**Связи.** Принадлежит диалогу через `dialogue_id` (диалог — не отдельная хранимая сущность, см. раздел «Value Objects»).

**Кто имеет право изменять.** Только AI Core (`ProcessUserMessageUseCase`), через `DialogueHistoryPort`.

**Use cases:** `ProcessUserMessageUseCase` (создание, изменение статуса); `BuildConversationContextUseCase` (чтение, `get_recent`).

### 1.3 FactDraft

**Назначение.** Временный черновик факта, ожидающий явного подтверждения пользователем перед сохранением в долговременную память (docs/01, §4.4; docs/02, §16.3).

**Жизненный цикл.** Создаётся командой `/запомнить`. Существует до одного из двух исходов: подтверждение (данные переносятся в новый `Fact`, черновик прекращает существование) или истечение срока (`expires_at`) без подтверждения. Черновик никогда не редактируется. Если пользователь отправляет `/запомнить` повторно, пока у него уже есть неподтверждённый черновик, новый черновик заменяет предыдущий — предыдущий перестаёт существовать (см. «Замечания архитектора»: правило не зафиксировано напрямую в docs/01–03, выбран самый простой вариант для MVP).

**Поля:** `draft_id`, `user_id`, `text`, `created_at`, `expires_at` — все обязательны.

**Инварианты:**
- Существует не дольше `expires_at − created_at` (TTL, конфигурируется — docs/02, §16.3, `FACT_DRAFT_TTL_SECONDS`).
- Не может быть подтверждён после истечения `expires_at`.
- Принадлежит ровно одному пользователю.
- **Для одного пользователя одновременно может существовать не более одного активного черновика.** Повторная команда `/запомнить` при уже существующем неподтверждённом черновике заменяет его новым — старый черновик и его текст теряются без отдельного пользовательского сценария отмены/подтверждения замены (такого сценария нет ни в docs/01, ни в этой модели).
- Подтверждение черновика — единственный путь появления `Fact`; `Fact` не создаётся напрямую.

**Кто создаёт.** Пользователь — командой `/запомнить`, через `RouteConversationCommandUseCase → StageFactUseCase`.

**Кто подтверждает.** Тот же пользователь — нажатием кнопки «Сохранить» или явным ответом, через `RouteConversationCommandUseCase → ConfirmFactUseCase`.

**Когда удаляется.** После подтверждения (данные переносятся в `Fact`) либо по истечении TTL.

**Use cases:** `StageFactUseCase` (создание), `ConfirmFactUseCase` (потребление → `Fact`).

### 1.4 Fact

**Назначение.** Долговременный факт о пользователе, сохранённый только по явному подтверждению (docs/01, §4.4).

**Жизненный цикл.** Создаётся исключительно через подтверждение `FactDraft`. Существует, пока пользователь явно не удалит его командой `/забыть`. Никогда не редактируется — только создаётся и удаляется.

**Поля:** `fact_id`, `user_id`, `text`, `confirmed_at` — все обязательны.

**Инварианты:**
- Не может существовать без предварительно подтверждённого черновика — прямого «создать факт» не существует.
- Принадлежит ровно одному пользователю (`user_id`).
- `text` не редактируется после создания.

**Связь с Profile.** Прямой связи нет — это важно проговорить отдельно, поскольку разница на первый взгляд не очевидна: `Fact` — факт **о пользователе**, `Profile` — стиль и ограничения **автора/ассистента**, единый для всех (docs/01, §2.3). Это разные субъекты по определению docs/01, и модель не должна их связывать — иначе факт стал бы частью профиля, а профиль перестал бы быть единым.

**Кто изменяет.** Создаёт `ConfirmFactUseCase`; удаляет `ForgetFactUseCase`. Текст никто не редактирует.

**Use cases:** `ConfirmFactUseCase` (создание), `ListFactsUseCase` (чтение), `ForgetFactUseCase` (удаление), `BuildConversationContextUseCase` (чтение, для контекста).

### 1.5 Document

**Назначение.** Метаданные документа заказчика в базе знаний (docs/01, §4.6).

**Жизненный цикл.** Создаётся администратором (загрузка файла и метаданных, `index_status = PENDING`) → индексируется асинхронно сервисом поиска → `index_status` становится `INDEXED` или `FAILED` → метаданные могут обновляться администратором → документ может быть удалён администратором (полное удаление, а не архивирование — в API нет метода архивации).

**Обязательные поля:** `document_id`, `title`, `index_status` (со значением по умолчанию `PENDING`).

**Необязательные поля:** `category: str | None` (структурно поле присутствует всегда, содержательно может быть не задано), `tags: tuple[str, ...]` (по умолчанию пусто).

**Инварианты:**
- `title` обязателен.
- Оригинал файла должен существовать в файловом хранилище, пока существует запись метаданных (целостность между SQLite и файловым хранилищем — обеспечивается оркестрацией use case'ов, а не самой сущностью).
- Удаление документа должно сопровождаться удалением его фрагментов из Qdrant и файла из хранилища — согласованность обеспечивает `RemoveDocumentUseCase`.

**Согласованность `index_status` и фрагментов:**
- `PENDING` означает, что индексация ещё не завершена — фрагменты в Qdrant для текущей версии документа отсутствуют либо не считаются актуальными.
- `INDEXED` означает успешное завершение индексации и согласованность состояния Qdrant с текущей версией документа. Наличие минимум одного `Fragment` требуется **только** для документов, из которых после валидации должен извлекаться непустой индексируемый текст, — жёсткое правило «`INDEXED` всегда означает наличие хотя бы одного `Fragment`» не вводится: корректный, но пустой или слишком короткий документ теоретически может дать ноль фрагментов и всё равно считаться успешно проиндексированным.
- `FAILED` означает, что документ не должен считаться доступным для семантического поиска. Частично записанные фрагменты неуспешной попытки индексации не должны оставаться доступными для поиска. Конкретный механизм очистки и атомарности перехода между попытками индексации use case обеспечивает на уровне реализации — физическая транзакционность будет конкретизирована при проектировании и реализации инфраструктурного слоя, здесь фиксируется только логическое требование.

**DocumentStatus vs DocumentIndexStatus.** В модели — только `DocumentIndexStatus` (`PENDING | INDEXED | FAILED`, docs/02, §9). Отдельный `DocumentStatus` (например, активен/удалён) не вводится: жизненный цикл документа бинарен — он либо существует, либо удалён навсегда, промежуточных состояний активности docs/01 не описывает.

**Связи:** 0..* `Fragment` (через `Fragment.source_id` при `source_type=DOCUMENT`); 0..* `DocumentCaseLink` (связь многие-ко-многим с `Case`).

**Кто изменяет.** Admin — заголовок/категорию/метки, создание и удаление (`UploadDocumentUseCase`, `UpdateDocumentUseCase`, `RemoveDocumentUseCase`). Search — `index_status`, по результату индексации (`IndexDocumentUseCase`, через тот же `DocumentRepositoryPort.update()`).

**Use cases:** `UploadDocumentUseCase`, `UpdateDocumentUseCase`, `RemoveDocumentUseCase`, `ListDocumentsUseCase` (admin); `IndexDocumentUseCase` (search — чтение + запись `index_status`).

### 1.6 Case

**Назначение.** Структурированный пример выполнения задачи — дополнительный пример для AI Core при формировании ответа (docs/01, §3). Не клиентский проект и не отдельная база знаний.

**Жизненный цикл.** Создаётся администратором (`status = ACTIVE`) → может обновляться → может быть архивирован (`status = ARCHIVED`). В отличие от `Document`, у `Case` нет операции физического удаления в порту (`CaseRepositoryPort` не имеет `delete()`, только `archive()`) — это осознанная асимметрия, соответствующая docs/01, §3 (кейс — переиспользуемый пример, не подлежащий обычному удалению, как документ).

**Обязательные поля:** `case_id`, `title`, `input_data`, `task_type`, `expected_approach`, `example_result`, `status` (по умолчанию `ACTIVE`).

**Необязательные поля:** нет — все содержательные поля обязательны: без любого из них объект перестаёт быть «структурированным примером» в смысле docs/01, §3.

**Статусы (`CaseStatus`):** `ACTIVE | ARCHIVED`.

**Инварианты:**
- `input_data`, `task_type`, `expected_approach`, `example_result` обязательны одновременно.
- Не является клиентским проектом и не является отдельной базой знаний (docs/01, §3 — смысловое, а не техническое ограничение).

**Открытый вопрос (не блокирует модель).** docs/01–03 не указывают, должны ли фрагменты архивированного кейса автоматически исключаться из поиска. Модель не предполагает такой автоматики — `ArchiveCaseUseCase` не вызывает `remove_from_index`; при необходимости это отдельное административное действие.

**Связи:** 0..* `Fragment` (через `source_id` при `source_type=CASE`); 0..* `DocumentCaseLink`.

**Кто изменяет.** Admin.

**Use cases:** `CreateCaseUseCase`, `UpdateCaseUseCase`, `ArchiveCaseUseCase`, `ListCasesUseCase` (admin); `LinkDocumentToCaseUseCase` (admin, изменяет связь, не сам `Case`); `IndexDocumentUseCase.index_case` (search, чтение).

### 1.7 DocumentCaseLink

**Назначение.** Связь многие-ко-многим между `Document` и `Case` (docs/01, §3, сценарий 10).

**Поля:** `document_id`, `case_id` — оба обязательны, вместе образуют составной идентификатор связи (отдельного `link_id` нет).

**Жизненный цикл.** Создаётся администратором при связывании документа с кейсом; удаляется при отвязывании. Собственных промежуточных состояний нет — связь либо существует, либо нет.

**Инварианты:**
- `document_id` и `case_id` должны ссылаться на существующие `Document`/`Case` (целостность обеспечивает use case/репозиторий, не сам класс).
- Связь не ограничивает доступ пользователей к документу вне кейса (docs/01, §3, сценарий 10 — явное требование).
- Пара `(document_id, case_id)` уникальна.

**Кто изменяет.** Admin, через `CaseRepositoryPort.link_document`/`unlink_document`.

**Use cases:** `LinkDocumentToCaseUseCase`.

### 1.8 Fragment

**Назначение.** Фрагмент текста документа или кейса — единица семантического поиска (docs/01, §4.6; RAG/Search).

**Жизненный цикл.** Создаётся только в процессе индексации (`IndexDocumentUseCase`: `DocumentChunker.split` → `EmbeddingPort.embed` → `VectorStorePort.upsert`). Никогда не редактируется. При переиндексации старые фрагменты удаляются (`remove_from_index`), новые создаются заново. Удаляется при удалении документа/кейса или при переиндексации.

**Обязательные поля:** `fragment_id`, `source_type`, `source_id`, `text`.

**Необязательные поля:** `score: float | None` — заполняется только как результат поиска; при индексации всегда `None` (один класс используется на обоих этапах, докс/03, §5).

**Что хранится.** Текст фрагмента и ссылка на источник (`source_type` + `source_id`).

**Что не хранится.** Сам вектор эмбеддинга — не поле Python-класса `Fragment`, а деталь физического хранения в Qdrant (`VectorStorePort.upsert` принимает фрагменты и векторы раздельными списками). Полный текст документа не дублируется — он остаётся в `Document`/файловом хранилище.

**Инварианты:**
- `source_id` ссылается ровно на один `Document` либо один `Case`, в зависимости от `source_type` — никогда на оба одновременно.
- `score` осмыслен только как результат поиска; при индексации отсутствует.
- **`Fragment` — неизменяемый объект.** Существующий фрагмент никогда не редактируется — ни текст, ни ссылка на источник.
- Любое изменение исходного документа или кейса приводит к удалению всего прежнего набора фрагментов этого источника (`remove_from_index`) и созданию нового набора заново — частичное обновление отдельных фрагментов не предусмотрено.
- Новый набор фрагментов, созданный при переиндексации, должен получать новые значения `FragmentId`, если используемая стратегия формирования идентификаторов не гарантирует безопасную идемпотентность повторной генерации тех же id для изменившегося текста. Конкретный алгоритм формирования `FragmentId` не относится к логической доменной модели и будет зафиксирован при проектировании и реализации соответствующих адаптеров и репозиториев — здесь фиксируется только это требование.

**Связи:** *—1 к `Document` (если `source_type=DOCUMENT`) либо *—1 к `Case` (если `source_type=CASE`).

**Кто изменяет.** Только Search (`IndexDocumentUseCase`) — создание и удаление через `VectorStorePort`. Никто не обновляет текст существующего фрагмента.

**Use cases:** `IndexDocumentUseCase` (создание/удаление), `SearchFragmentsUseCase` (чтение).

### 1.9 AuditEntry

**Назначение.** Запись административного действия для аудита (docs/01, §4.8).

**Жизненный цикл.** Создаётся один раз в момент успешно выполненного административного действия. Далее неизменна, не удаляется — append-only журнал.

**Поля:** `correlation_id`, `action`, `occurred_at` — все обязательны.

**Инварианты:**
- Создаётся только вместе с успешно завершённым действием — неудачные попытки фиксируются в `SystemEventEntry`/техническом журнале, а не здесь (docs/02, §11).
- Никогда не редактируется и не удаляется.
- Не содержит содержимого документа/кейса — только факт действия и обезличенные идентификаторы (docs/01, §4.8).

**Связи.** `correlation_id` — не внешний ключ, а сквозной идентификатор трассировки, может совпадать с `correlation_id` связанного запроса, но не является ссылкой на хранимую сущность.

**Кто создаёт.** Любой use case модуля `admin`, через `AuditPort.record()`.

**Use cases:** `UploadDocumentUseCase`, `UpdateDocumentUseCase`, `RemoveDocumentUseCase`, `CreateCaseUseCase`, `UpdateCaseUseCase`, `ArchiveCaseUseCase`, `LinkDocumentToCaseUseCase`.

---

### 1.10 TechnicalLogEvent

**Назначение.** Техническое событие обработки запроса — только идентификатор и статус, без текста (docs/02, §14).

**Жизненный цикл.** Создаётся в момент события. **Не хранится в базе данных приложения** — это строка в stdout/stderr, забираемая внешним сборщиком логов (Docker локально, штатная система сборки логов контейнеров в Yandex Cloud — docs/01, §4.8). С точки зрения приложения объект существует только во время формирования строки лога.

**Поля:** `correlation_id`, `event`, `status`, `occurred_at` — все обязательны.

**Инварианты:**
- Не содержит текста реплик, ключей, паролей, содержимого документов (docs/01, §4.8 — жёсткое ограничение).

**Связи.** `correlation_id` связывает запись с историей диалога и аудитом одного и того же запроса при разборе инцидента (docs/02, §14) — конвенция трассировки, а не хранимая связь.

**Кто создаёт.** Любой модуль через `LoggerPort.log_event()` — AI Core, Telegram-адаптер, Admin, Search и т. д.

**Use cases.** Не привязан к одному use case — cross-cutting порт; основной источник — `ProcessUserMessageUseCase`.

---

### 1.11 SystemEventEntry

**Назначение.** Ошибка, требующая последующего анализа — единственный вид технического события, дополнительно попадающий в SQLite (docs/01, §4.8).

**Жизненный цикл.** Создаётся при ошибке, требующей анализа. Далее не редактируется. Удаление/срок хранения не специфицированы (docs/02, §14 — «оставлен открытым эксплуатационным параметром»).

**Поля:** `correlation_id`, `description`, `occurred_at`.

**Инварианты.** Аналогично `TechnicalLogEvent` — без чувствительных данных; `description` — техническое описание, не пользовательский текст.

**Связи.** `correlation_id` (см. `TechnicalLogEvent`); единственная сущность из журнального блока, доступная на чтение через `AnalyticsReadPort` (docs/02, §12) для будущего аналитического модуля.

**Кто создаёт.** Любой модуль через `LoggerPort.log_system_error()`.

**Use cases.** Не завязана на конкретный use case; порт используется при обработке ошибок (docs/02, §11).

## 2. Value Objects

| VO | Тип | Назначение |
|---|---|---|
| `UserId` | `NewType(str)` | Идентификатор пользователя Telegram; владелец `Fact`/`FactDraft` |
| `ChatId` | `NewType(str)` | Идентификатор чата Telegram; используется также как идентификатор диалога (см. унификацию ниже) |
| `DialogueMessageId` | `NewType(str)` | Идентификатор отдельной реплики |
| `ProfileId` | `NewType(str)` | Определён, но не используется в `Profile` (см. ниже) |
| `FactId` | `NewType(str)` | Идентификатор подтверждённого факта |
| `FactDraftId` | `NewType(str)` | Идентификатор черновика факта |
| `DocumentId` | `NewType(str)` | Идентификатор документа |
| `CaseId` | `NewType(str)` | Идентификатор кейса |
| `FragmentId` | `NewType(str)` | Идентификатор фрагмента |
| `CorrelationId` | `NewType(str)` | Идентификатор трассировки запроса — не идентификатор сущности и не внешний ключ (см. пояснение ниже) |

Все идентификаторы реализованы как `typing.NewType(str)` в одном файле (`shared/domain/identifiers.py`), а не отдельными dataclass-классами — этого достаточно, чтобы различать «чей это id» на уровне типов, без накладных расходов на отдельный класс под каждый идентификатор.

**Унификация:**
- **`DialogueId` отдельно не вводится.** `DialogueMessage.dialogue_id` имеет тип `ChatId`. Один диалог в MVP — это одна переписка пользователя с ботом в Telegram (один пользователь = один чат), поэтому отдельный идентификатор избыточен.
- **`UserId` и `ChatId` сознательно НЕ объединяются**, хотя в приватном чате Telegram их значения часто совпадают. `Fact`/`FactDraft` принадлежат пользователю (`UserId`), история диалога — чату (`ChatId`): это разные оси группировки, и при появлении нового канала (docs/02, §12 — например, группового чата или другого мессенджера) они разойдутся.
- **`ProfileId` не используется в `Profile`.** Профиль — синглтон без сценария «получить по id» (docs/01, §2.3): единственный метод порта — `get_profile()` без параметров. Тип определён в общих идентификаторах на случай будущего версионирования, но сама сущность `Profile` его не хранит — вне MVP.
- **`Timestamp` как отдельный value object не вводится.** Везде используется стандартный `datetime`; собственная обёртка не добавляет проверяемого инварианта, которого не даёт сам тип, и не оправдана для MVP.

**`CorrelationId` — особый случай среди value objects.** В отличие от остальных идентификаторов, `CorrelationId` не идентифицирует доменную сущность:
- это идентификатор трассировки одного запроса, а не первичный ключ какой-либо сущности;
- он не выражает отношение владения (в отличие от `UserId` у `Fact`/`FactDraft` или `DocumentId` у `Fragment`);
- он не должен использоваться как внешний ключ между таблицами при проектировании физической схемы (будет зафиксировано при проектировании и реализации инфраструктурного слоя) — совпадение значения не гарантирует ссылочной целостности, только временную и логическую связанность одного запроса;
- совпадение `CorrelationId` у записей `DialogueMessage`, `AuditEntry`, `TechnicalLogEvent` и `SystemEventEntry` позволяет сопоставить историю обработки, аудит и технические события одного запроса при диагностике инцидента (docs/02, §14) — это конвенция трассировки, а не структурная связь модели.

## 5. Связи между сущностями

Пример цепочки из задания (`Profile → Fact → DialogueMessage → Document → Fragment → Case`) **не соответствует утверждённой модели** и не используется — в реальной модели такой сквозной цепочки нет: `Profile` не связан ни с чем напрямую, `Fact` не связан с `Document`, `DialogueMessage` не связан с `Document`. Ниже — фактические связи:

- **Пользователь** (не хранимая сущность, см. раздел 7) `1 — *` `Fact` (через `Fact.user_id`)
- **Пользователь** `1 — *` `FactDraft` (через `FactDraft.user_id`)
- **Диалог** (группировка по `ChatId`, не хранимая сущность) `1 — *` `DialogueMessage` (через `DialogueMessage.dialogue_id`)
- `Document` `1 — *` `Fragment` (через `Fragment.source_id` при `source_type=DOCUMENT`)
- `Case` `1 — *` `Fragment` (через `Fragment.source_id` при `source_type=CASE`)
- `Document` `* — *` `Case` через `DocumentCaseLink` (association-сущность, не принадлежит ни одной из сторон)
- `Profile` — без связей с другими сущностями
- `AuditEntry`, `TechnicalLogEvent`, `SystemEventEntry` — связаны друг с другом и с `DialogueMessage` только через `CorrelationId` (сквозной идентификатор трассировки запроса, не внешний ключ и не отношение владения)

## 7. Что не хранится

Существуют только во время выполнения запроса — не персистентны:

- **`IncomingMessage`, `OutgoingResponse`** (`ai_core/domain/message.py`) — канало-независимое представление одного запроса/ответа; их постоянный след — соответствующие `DialogueMessage`.
- **`ConversationContext`** (`shared/application/conversation_context.py`) — собирается заново на каждый запрос из уже сохранённых `Profile`/`Fact`/`DialogueMessage`/`Fragment`; сохранять сам объект не нужно — он воспроизводим из первичных данных.
- **`LLMRequestContext`, `LLMResponse`** (`llm/application/ports.py`) — контракт одного вызова LLM Adapter.
- **`SearchQuery`/`SearchResult` как отдельные типы не вводятся** — поисковый запрос передаётся обычной строкой (`str`), а результат — тот же `Fragment` с заполненным `score`; отдельный DTO избыточен (уже решение docs/03, §5 — Fragment используется на обоих этапах).
- **Токен сессии администратора** (`str`, возвращаемый `AdminAuthPort.authenticate`) — не хранится как сущность БД; сессия — подписанная cookie (docs/02, §13), серверного хранилища сессий в MVP нет.
- **`Settings`** (`config/settings.py`) — конфигурация процесса (переменные окружения), не бизнес-данные и не часть доменной модели.
- **Пользователь и администратор как хранимые сущности** — система не ведёт собственной записи о пользователе (нет полей «имя», «дата регистрации» и т. п.): пользователь идентифицируется исключительно `UserId`/`ChatId`, полученными от Telegram Bot API при каждом обращении. Администратор тоже не хранимая сущность — единственная учётная запись задаётся переменными окружения (docs/01, §4.7), а не записью в БД.

## 8. Границы агрегатов

Для MVP доменная модель намеренно не вводит сложные составные агрегаты. Большинство сущностей имеют самостоятельный жизненный цикл, а межхранилищные и межмодульные инварианты обеспечиваются application use case'ами, а не составным объектом-агрегатом с общим корнем.

Из этого явно следует:
- В модели нет ни одного агрегата с дочерними сущностями внутри одного корня, чью согласованность требовалось бы поддерживать атомарно на уровне доменного объекта. Каждая сущность имеет собственный репозиторий/порт и собственный жизненный цикл (раздел 1, раздел 9).
- Называть каждую сущность «Aggregate Root» в строгом DDD-смысле было бы слишком сильной формулировкой: `Profile`, `DialogueMessage`, `FactDraft`, `Fact`, `Document`, `Case`, `Fragment` — это самостоятельные сущности с собственным жизненным циклом, а не корни составных объектных графов с дочерними сущностями.
- `DocumentCaseLink` — association-сущность, связывающая два независимых объекта (`Document` и `Case`). Она не является полноценным Aggregate Root и не принадлежит ни одному из связываемых объектов.
- `AuditEntry`, `TechnicalLogEvent`, `SystemEventEntry` — самостоятельные append-only журнальные записи. Их не обязательно называть агрегатами: у них нет ни дочерних объектов, ни инвариантов, требующих согласованного изменения нескольких записей одновременно.
- Границы консистентности в MVP обеспечиваются application use case'ами (например, `RemoveDocumentUseCase` последовательно убирает документ, его фрагменты и файл — docs/03, §9) и репозиториями, а не декларативными границами агрегата на уровне доменной модели.

Соответствие модулям (bounded context, docs/02) — это группировка по владению (раздел «Ownership сущностей»), а не структура агрегатов:
- `profile` — `Profile`.
- `memory` — `DialogueMessage`, `FactDraft`, `Fact`: три независимые сущности без общего объекта «Диалог» или «Память пользователя».
- `knowledge_base` — `Document`, `Case` (независимые сущности) и `DocumentCaseLink` (association-сущность между ними).
- `search` — `Fragment`.
- `logging_audit` — `AuditEntry`, `TechnicalLogEvent`, `SystemEventEntry` (независимые журнальные записи).

Классы-обёртки вида `MemoryAggregate`/`KnowledgeBaseAggregate` модель не вводит: группировка выше существует только на уровне документации и модулей (docs/03), а не как отдельный код или доменный тип.

## Ownership сущностей

«Модуль-владелец» — модуль, который определяет доменный класс сущности и порт её хранения (`application/ports.py`), а не любой модуль, который может инициировать её изменение.

| Сущность | Модуль-владелец | Кто создаёт | Кто изменяет/удаляет |
|---|---|---|---|
| Profile | `profile` | `SeedProfileIfMissingUseCase` (только при пустой БД) | Никто в runtime — вне приложения, прямым редактированием конфигурации/БД |
| DialogueMessage | `memory` | `ProcessUserMessageUseCase` (ai_core, через `DialogueHistoryPort`) | `ProcessUserMessageUseCase` — только `processing_status` реплики пользователя; текст никем не редактируется, удаления нет |
| FactDraft | `memory` | `StageFactUseCase` (через `RouteConversationCommandUseCase`) | `ConfirmFactUseCase` (переносит данные в `Fact`, черновик прекращает существование); истечение TTL |
| Fact | `memory` | `ConfirmFactUseCase` | `ForgetFactUseCase` (удаление); текст не редактируется никем |
| Document | `knowledge_base` | `UploadDocumentUseCase` (admin, через `DocumentRepositoryPort`) | `UpdateDocumentUseCase`/`RemoveDocumentUseCase` (admin — метаданные, удаление); `IndexDocumentUseCase` (search — только `index_status`, через тот же порт) |
| Case | `knowledge_base` | `CreateCaseUseCase` (admin) | `UpdateCaseUseCase`/`ArchiveCaseUseCase` (admin) |
| DocumentCaseLink | `knowledge_base` | `LinkDocumentToCaseUseCase` (admin, через `CaseRepositoryPort`) | `LinkDocumentToCaseUseCase` (admin — unlink) |
| Fragment | `search` | `IndexDocumentUseCase` (через `VectorStorePort`) | `IndexDocumentUseCase` — единственный писатель; удаление при переиндексации/удалении источника |
| AuditEntry | `logging_audit` | Use case'ы модуля `admin` (через `AuditPort`) | Никто — append-only, не изменяется и не удаляется |
| TechnicalLogEvent | `logging_audit` | Любой модуль (через `LoggerPort`) | Никто — не хранится приложением, не изменяется |
| SystemEventEntry | `logging_audit` | Любой модуль (через `LoggerPort`) | Никто — append-only, ретеншн не специфицирован |

**Важное уточнение.** Модуль, отличный от владельца, может инициировать изменение сущности — но только через порт модуля-владельца, а не напрямую. Пример: Search вызывает `DocumentRepositoryPort.update()`, чтобы записать `index_status`, — это не делает Search владельцем `Document`; владельцем остаётся `knowledge_base`, потому что именно он определяет доменный класс и порт хранения. Прямой доступ к адаптеру чужого модуля (например, к `sqlite_document_repository.py` из `search`) запрещён — соответствует правилам импортов (docs/03, §5).

## 10. Проверка модели

1. **Дублирующиеся сущности.** Не обнаружены — 11 сущностей, каждая представлена одним классом в одном модуле. `Fact`/`FactDraft` — не дублирование, а осознанно разные сущности с разным жизненным циклом (docs/02, §16.3).
2. **Сущности без владельца.** Не обнаружены — каждая сущность принадлежит ровно одному модулю: Profile → `profile`; DialogueMessage/Fact/FactDraft → `memory`; Document/Case/DocumentCaseLink → `knowledge_base`; Fragment → `search`; AuditEntry/TechnicalLogEvent/SystemEventEntry → `logging_audit`.
3. **Нарушение границ модулей.** Не обнаружено — связи между сущностями разных модулей выражены только через value object-идентификаторы (например, `Fragment.source_id: DocumentId | CaseId`), ни одна сущность не импортирует чужой `domain`-класс напрямую; соответствует правилам импортов docs/03, §5.
4. **Двойное хранение SQLite + Qdrant без причины.** Не обнаружено. `Document` хранится в SQLite (метаданные) и файловой системе (оригинал) — не в Qdrant; `Fragment` — только в Qdrant. Единственное «двойное» хранение (метаданные + файл для `Document`) прямо предписано docs/01, §4.6.
5. **ORM-зависимости.** Не обнаружены — ни одного упоминания ORM-библиотек, все сущности — dataclass.
6. **SQL-таблицы.** Не обнаружены — ни одного DDL/CREATE TABLE.
7. **API-модели.** Не обнаружены — ни одного упоминания FastAPI/response-моделей.
8. **DTO.** Явно вынесены в отдельный раздел 7 («Что не хранится») и не смешаны с сущностями домена.
9. **Pydantic-модели.** Не обнаружены — документ выдержан в dataclass-мышлении на всём протяжении.
10. **Противоречия docs/01–03.** Не обнаружены в итоговой версии — места, где пример из задания расходился с утверждённой архитектурой, скорректированы и явно отмечены (см. «Замечания архитектора» ниже), а не приняты молча.
11. **Один модуль-владелец на сущность.** Подтверждено разделом «Ownership сущностей» — для всех 11 сущностей указан ровно один модуль-владелец; случаи, когда изменение инициирует другой модуль (Search → `Document.index_status`), явно помечены как «через порт владельца», а не как совладение.
12. **Association-сущности не названы сложными агрегатами без необходимости.** `DocumentCaseLink` явно обозначена как association-сущность, а не Aggregate Root (раздел 8); журнальные сущности названы «самостоятельными записями», а не агрегатами.
13. **`CorrelationId` не используется как внешний ключ.** Подтверждено разделом 2 (Value Objects) и описаниями журнальных сущностей: совпадение значения используется только для трассировки при диагностике, не для связывания записей в БД.
14. **Состояние индексации не допускает доступности частично записанных фрагментов.** Раздел 1.5: при `FAILED` частично записанные фрагменты неуспешной попытки не должны оставаться доступными для поиска; конкретный механизм будет определён на этапе реализации соответствующих адаптеров и репозиториев.
15. **Новых сущностей, полей или пользовательских функций, не следующих из docs/01–03, не появилось.** Единственное новое явное решение архитектора в этой редакции — правило «не более одного активного `FactDraft` на пользователя» — зафиксировано как замечание архитектора (решение по умолчанию для MVP), а не как новый пользовательский сценарий (сценария отмены/подтверждения замены не вводится).

### Перечень Aggregate Root
MVP не вводит составных агрегатов с дочерними сущностями, поэтому список «Aggregate Root» в строгом DDD-смысле не имеет содержательного отличия от списка сущностей — это намеренно (раздел 8):
- **Самостоятельные сущности с собственным жизненным циклом** (не требуют статуса «агрегат», чтобы существовать корректно): Profile, DialogueMessage, FactDraft, Fact, Document, Case, Fragment.
- **Association-сущность, не Aggregate Root:** DocumentCaseLink — связывает Document и Case, не принадлежит ни одному из них.
- **Самостоятельные append-only журнальные записи** (не требуют статуса «агрегат»): AuditEntry, TechnicalLogEvent, SystemEventEntry.

### Замечания архитектора

Ниже — только решения, которые не зафиксированы напрямую в docs/01–03 и потребовали выбора архитектора, либо места, где пример из задания расходился с утверждённой моделью. Предположения не выдаются за утверждённые требования.

1. **Разделение `Profile.style` на `identity` и `voice` не принято.** docs/01, §2.3 упоминает «стиль, тон и ограничения» — но не выделяет отдельного аспекта «роль/позиционирование ассистента» (`identity`); в docs/01–03 такое понятие не встречается ни разу. Фактический domain-класс хранит стиль и тон одним полем `style: str`, без структурного деления. Раздельные `identity`/`voice` не следуют из документов и не совпадают с кодом — оставлены текущие поля (`style`, `constraints`). Отдельно отклонены (тем же основанием, что и ранее) `audience`, `preferences`, `knowledge_base_links`, `task_templates_usage` — `knowledge_base_links` прямо противоречил бы docs/01, §4.6 («База знаний едина для всех пользователей ассистента»), `task_templates_usage` вводил бы не описанную в docs/01–03 связь профиля с кейсами.
2. **`DocumentStatus`, `FactStatus`, `FactDraftStatus` не введены** — обоснование в разделах 1.5 и 3: жизненный цикл документа бинарен, а состояние факта/черновика выражено выбором репозитория, а не полем-статусом на одном классе.
3. **Стратегия «один активный `FactDraft` на пользователя» — новое решение архитектора, не описанное в docs/01–03.** Из двух вариантов (замена черновика новым либо отказ в создании нового до подтверждения/истечения текущего) выбран самый простой для MVP — замена. Отказ потребовал бы дополнительной пользовательской обратной связи («у вас уже есть неподтверждённый черновик, сначала подтвердите или дождитесь истечения») — отдельного сценария для этого в docs/01 нет, а введение такого поведения было бы расширением UX сверх MVP. Замена не требует нового пользовательского сценария и совместима с уже описанным поведением `/запомнить` (docs/01, сценарий 4).
4. **Переосмысление термина «Aggregate Root» (раздел 8).** Первая редакция документа называла каждую сущность отдельным Aggregate Root — формулировка избыточно сильная для модели, где нет ни одного составного агрегата с дочерними сущностями. Скорректировано: большинство сущностей описаны как «самостоятельные сущности с собственным жизненным циклом», `DocumentCaseLink` — как association-сущность, журнальные записи — как «самостоятельные append-only записи». Это уточнение терминологии, не изменение структуры модели.
5. **Логическая, а не физическая согласованность `DocumentIndexStatus` с Qdrant (раздел 1.5).** Зафиксировано только требование к результату («`FAILED` не должен оставлять частично записанные фрагменты доступными для поиска», «`INDEXED` не обязан означать ≥1 фрагмента»), без описания способа его обеспечения (транзакции, двухфазные операции, компенсирующие действия и т. п.) — конкретный механизм не относится к логической доменной модели и будет зафиксирован при проектировании и реализации инфраструктурного слоя.
6. **Цепочка связей из примера задания (`Profile → Fact → DialogueMessage → Document → Fragment → Case`) заменена на фактическую структуру связей** (раздел 5) — пример не отражает ни одной реально существующей ссылки между этими сущностями в коде.
7. **Связь `Fact ↔ Profile` из задания заменена явным «связи нет»** — Fact принадлежит пользователю, Profile — общий для всех; связывать их означало бы нарушить единственность профиля (docs/01, §2.3).
8. **Асимметрия Document/Case по удалению отмечена явно** (раздел 1.5–1.6): `Document` можно удалить физически, `Case` — только архивировать. Это уже заложено в портах `docs/03`, а не новое решение; здесь оно впервые сформулировано как явный инвариант модели.
