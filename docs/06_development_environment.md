## 2. Назначение документа

Документ фиксирует инженерные решения об окружении разработки — то, что стоит между утверждённой архитектурой (`docs/02–05`) и написанием кода реализации. Он определяет: состав инструментов разработки, структуру конфигурационных файлов и переменных окружения, способ управления зависимостями, архитектуру Docker-окружения, порядок запуска приложения через composition root, принципы конфигурирования и логирования на уровне окружения, устройство тестового окружения, единые правила разработки, итоговую структуру репозитория и контрольный список готовности.

**Вне области ответственности этого документа:**
- архитектурные решения (`docs/02`), доменная модель (`docs/04`), внутренние контракты (`docs/05`) — не пересматриваются и не дополняются;
- бизнес-логика use case'ов;
- конкретные команды установки инструментов и версии пакетов;
- содержимое конфигурационных файлов (`Dockerfile`, `docker-compose.yml`, `pyproject.toml`, `.env.*`, `Makefile`) — они не создаются и не приводятся целиком, только описываются архитектурно;
- исходный код реализации.

## Принципы воспроизводимости

Любой разработчик, получивший репозиторий, должен иметь возможность полностью воспроизвести окружение — установить зависимости, поднять Docker-окружение, запустить приложение и тесты — без принятия дополнительных решений об инструментах, структуре конфигурации или порядке запуска. Все такие решения уже зафиксированы в этом документе (разделы 3–12); задача разработчика — выполнить их, а не выбирать заново.

Если для воспроизведения окружения требуется решение, не описанное в этом документе, — это признак того, что документ нужно дополнить, а не что решение можно принять неявно на месте.

## 4. Структура конфигурации проекта

Три файла с разным назначением, различающиеся тем, где они существуют и что в них допустимо хранить:

| Файл | Коммитится в репозиторий | Содержит | Назначение |
|---|---|---|---|
| `.env.example` | Да (уже создан, docs/03) | Полный список переменных окружения с комментариями, без значений секретов | Единственный источник истины о том, какие переменные вообще существуют (раздел 5) — шаблон для остальных файлов |
| `.env.local` | Нет | Значения для локальной разработки конкретного разработчика (локальный `SQLITE_PATH`, `QDRANT_URL=http://localhost:6333` и т. п., собственные тестовые ключи API) | Создаётся каждым разработчиком самостоятельно на основе `.env.example`; никогда не содержит боевых секретов |
| `.env.production` | Нет и не должен существовать как файл в репозитории | Боевые значения (реальные токены, ключи, хеш пароля администратора) | В `docs/01` (§4.7, §8) и `docs/02` (§13) уже зафиксировано: секреты передаются через переменные окружения контейнера/платформы (Yandex Cloud), а не через файл, который можно закоммитить по ошибке — «`.env.production`» здесь обозначает не файл, а набор переменных, управляемых средствами развёртывания |

Реальные значения переменных в этом документе не публикуются нигде — только назначение и пример, не являющийся секретом (раздел 5).

## 6. Управление зависимостями

- **Менеджер пакетов: `uv`.** Решение зафиксировано этим документом (ни один из docs/01–05 менеджер зависимостей не выбирал). `uv` совместим с уже существующим `pyproject.toml` (backend — `setuptools`, docs/03) без изменения файла сборки и хорошо соответствует цели «реалистично для одного разработчика за 3–4 недели» (docs/02, §14) — один быстрый инструмент вместо нескольких.
- **Файл зависимостей:** `pyproject.toml` (уже существует) — секция `[project.dependencies]`. Дополнительно появится lock-файл `uv.lock` при первой установке — он не создаётся в рамках этой задачи (раздел «Ограничения»).
- **Правила обновления:** обновление версий зависимостей — осознанное отдельное действие разработчика, не выполняется автоматически при обычной установке; каждое обновление lock-файла — отдельное, рецензируемое изменение, как и любое другое изменение кода.
- **Правила фиксации версий:** точные версии фиксируются в lock-файле (коммитится в репозиторий и является источником истины для воспроизводимой установки); в `pyproject.toml` — только сами зависимости и, при необходимости, минимальные/поддерживаемые диапазоны версий (ожидаемый состав уже намечен в комментарии `pyproject.toml`, docs/03: `fastapi`, библиотека клиента Telegram Bot API, `qdrant-client`, `httpx`, `argon2-cffi`/`passlib`).

## 7. Docker

**Назначение.** Единообразная среда выполнения для локальной разработки и продакшена (docs/01, §5, §8). Docker в этом проекте не служит границей между модулями — вся бизнес-логика работает в одном процессе одного контейнера (docs/02, §1 — модульный монолит); Docker здесь — про воспроизводимость окружения, а не про декомпозицию системы.

**Состав окружения (архитектурно, без содержимого `docker-compose.yml`):**
- **Сервис приложения** — контейнер, собранный из образа проекта, единственный процесс которого — FastAPI/ASGI-приложение `dekoder` (`main.py` → composition root, раздел 8). К нему подключены два постоянных тома: один — под файл SQLite (путь `SQLITE_PATH`), второй — под файловое хранилище документов (`DOCUMENTS_STORAGE_PATH`); оба — постоянные тома, а не файловый слой самого контейнера (docs/02, §16.4).
- **Сервис Qdrant** — официальный образ Qdrant, с собственным томом для данных векторного индекса. Не имеет отношения к бизнес-логике модулей — используется только через `VectorStorePort` (docs/05, §1.5).
- **SQLite не является отдельным сервисом** — это файл на томе сервиса приложения, не отдельный контейнер (docs/02, §1).

**Взаимодействие сервисов:** сервис приложения обращается к Qdrant по внутреннему сетевому имени сервиса в Docker-сети (`QDRANT_URL` указывает на это имя, а не на `localhost`, — отличие локального запуска в Docker Compose от запуска приложения на хосте напрямую). Наружу из docker-compose открыт только сервис приложения (Telegram webhook и HTTP панели администратора — оба уже описаны в docs/02/05); Qdrant не публикуется наружу.

**Переменные окружения** передаются сервису приложения из `.env.local` (локальная разработка) либо из секретов/переменных окружения оркестратора (Yandex Cloud) — не хранятся в самом `docker-compose.yml` (раздел 4).

## 8. Структура запуска приложения

Единственная точка сборки приложения — composition root (`docs/03`, §8, §11; `docs/05`, §1). Порядок инициализации:

```
main.py
   ↓
composition.bootstrap.create_app()
   ↓
config.settings.load_settings()              →  Settings (раздел 9)
   ↓
infrastructure.sqlite.connection
   .SqliteConnectionFactory(settings.sqlite_path)
   ↓
composition.container.build_container(settings)  →  Repositories/Adapters → Use Cases (через DI)
   ↓
Регистрация driving-адаптеров
   (Telegram — modules/telegram; HTTP панели администратора — modules/admin/adapters/http)
   ↓
Восстановление незавершённых заданий индексации (docs/02, §9)
   ↓
Application Start
```

Composition root — единственное место, которому разрешено одновременно знать про порты и конкретные адаптеры всех модулей (уже зафиксировано в `docs/03`, §8 и `docs/05`, §1/§6) — этот документ не вводит новых правил, только фиксирует порядок шагов, необходимый для настройки окружения запуска.

## 9. Конфигурация приложения

- **Загрузка.** Единственная точка чтения переменных окружения — `config.settings.load_settings()` (docs/03, «config»). Ни один другой модуль не обращается к `os.environ` напрямую.
- **Валидация.** Принцип для окружения разработки: приложение должно отказываться стартовать, если обязательная переменная (раздел 5) не задана или задана некорректно, — ошибка конфигурации обязана останавливать процесс на шаге `load_settings()`/сразу после него, до регистрации driving-адаптеров (раздел 8), а не проявляться позже как ошибка первого запроса. Конкретный механизм валидации (что именно проверяется и как) — деталь реализации, не фиксируется этим документом.
- **Неизменяемость после запуска.** `Settings` — иммутабельный объект (уже `@dataclass(frozen=True)` в коде, docs/03). Применение новых значений переменных окружения требует перезапуска процесса — это уже согласуется с правилом переключения LLM/Embedding-провайдера через конфигурацию и перезапуск (docs/02, §16.2, §9).
- **Dependency Injection.** `Settings` передаётся в `build_container`, который создаёт конкретные адаптеры и внедряет их в use case'ы через конструкторы (docs/03, §8, §11; docs/05, §1). Это единственный способ получить значения конфигурации внутри системы — не через прямое чтение переменных окружения где-либо ещё.

## 10. Логирование

Окружение не добавляет ничего сверх уже зафиксированного в `docs/01` §4.8, `docs/02` §14 и `docs/05` §12 — здесь фиксируется только то, что из этого следует для инфраструктуры окружения:

- **Уровень логирования.** Не настраивается через переменные окружения в MVP (раздел 5 — категория Logging пуста); технические журналы пишутся безусловно.
- **Технические журналы.** Вывод в stdout/stderr в структурированном виде. В Docker Compose собираются самим Docker (стандартный драйвер логирования контейнера); в Yandex Cloud — штатной системой сбора логов контейнеров. Окружение не требует отдельного сервиса сбора логов.
- **Аудит.** Отдельная таблица в том же файле SQLite (`SQLITE_PATH`), что и остальные данные приложения — не требует отдельного тома или сервиса.
- **Системные события.** Аналогично аудиту — та же база SQLite.
- **Хранение логов.** Технические журналы приложением не хранятся (внешний сборщик, вне периметра приложения); аудит и системные события хранятся в SQLite на том же постоянном томе, что и остальные данные (раздел 7) — отдельный том для журналов не вводится.

## 11. Тестовое окружение

- **Отдельная конфигурация.** Тесты используют собственный набор переменных окружения (например, `.env.test` или переменные, переданные тестовому процессу напрямую), отдельный от `.env.local` — тесты не должны читать или изменять данные, которыми пользуется разработчик при обычном запуске.
- **Тестовая БД.** Отдельный файл SQLite (например, временный файл на время тестового запуска), никогда не тот же файл, что указан в `SQLITE_PATH` при обычной разработке.
- **Тестовый Qdrant.** Окружение обязано допускать переопределение `QDRANT_URL` для тестового запуска (отдельный контейнер/коллекция) — конкретный выбор между реальным тестовым контейнером и тестовым двойником `VectorStorePort` не фиксируется этим документом: это решение уровня реализации тестов, а не окружения.
- **Изоляция тестов.** Тесты не используют `.env.local`/боевые переменные; не разделяют состояние (файл SQLite, коллекцию Qdrant) ни с обычным запуском приложения, ни друг с другом при параллельном выполнении.
- **Принципы запуска.** Тесты запускаются тем же менеджером зависимостей (`uv`, раздел 6). Поскольку use case'ы зависят от портов, а не от конкретных адаптеров (docs/03, §5; docs/05, §6), большинству тестов не требуется поднимать Docker/Qdrant/SQLite вообще — тестовые двойники подставляются вместо портов; Telegram- и HTTP-адаптеры для таких тестов не запускаются.

## 12. Правила разработки

- **Форматирование и линтер.** Единый инструмент для форматирования и статического анализа — `ruff` (согласуется с выбором `uv`, тот же экосистемный набор, docs/02 §14 — минимум инструментов для одного разработчика). Конфигурационный файл не приводится (раздел «Ограничения»).
- **Статическая типизация.** Обязательна — весь существующий код уже использует `from __future__ import annotations` и полные аннотации типов (docs/03). Статический type checker (например, `mypy` или `pyright`) обязателен для проверки соответствия реализаций портам (`Protocol`) — конкретный выбор инструмента и его настройка не фиксируются этим документом.
- **Структура импортов.** Уже зафиксирована в `docs/03`, §5, и статически проверена (`docs/03`, §15) — не повторяется здесь; при реализации эта проверка должна стать частью повторяемого процесса (линтер/CI), а не разовым скриптом.
- **Стиль комментариев.** Уже установлен во всём существующем коде: docstring на уровне модуля/класса объясняет «почему», не «что»; комментарии внутри тела функций-заглушек не используются.
- **Соглашения об именовании.** Уже видны из кода: `snake_case` для функций, переменных и файлов; `PascalCase` для классов; суффикс `Port` — для протоколов, `UseCase` — для use case'ов, `Repository`/`Adapter`/`Store` — для реализаций outbound-портов.

## Версионирование окружения

Любое изменение состава Docker-окружения, `pyproject.toml`, `.env.example` или структуры конфигурации (разделы 4–7) считается изменением, затрагивающим окружение разработки, и должно сопровождаться обновлением этого документа в том же изменении (том же коммите/PR), а не отдельным последующим шагом. Документ иначе быстро перестаёт соответствовать фактическому состоянию репозитория и теряет ценность как источник истины для воспроизведения окружения (см. «Принципы воспроизводимости»).

## 15. Результат этапа

**Зафиксированные инженерные решения:**
- менеджер зависимостей — `uv`, файл зависимостей — `pyproject.toml` + `uv.lock`;
- три уровня конфигурации (`.env.example` / `.env.local` / переменные окружения продакшена) с чётким разделением ответственности;
- полный перечень из 15 переменных окружения по 8 категориям (раздел 5);
- архитектура Docker-окружения: сервис приложения + сервис Qdrant, SQLite — файл на томе, а не отдельный сервис;
- порядок запуска через composition root (bootstrap → settings → infrastructure → container → driving-адаптеры → start) — без изменений относительно `docs/03`/`docs/05`, зафиксирован как процесс окружения;
- принципы конфигурирования: fail-fast валидация при старте, неизменяемость `Settings` после запуска, единственная точка DI;
- логирование на уровне окружения — без новых переменных, без отдельного сервиса сбора;
- устройство тестового окружения — изоляция БД/Qdrant/конфигурации от разработческого запуска;
- единые правила разработки — `ruff` (форматирование и линт), обязательная статическая типизация, уже установленные соглашения об именовании и импортах.

**Что считается подготовленным:** полное описание окружения, достаточное, чтобы любой разработчик мог создать `Dockerfile`, `docker-compose.yml`, `.env.local`, lock-файл зависимостей и каталог `tests/` без дополнительных архитектурных решений.

**Что будет выполняться на следующем этапе (реализация):** непосредственное создание `Dockerfile`, `docker-compose.yml`, `.dockerignore`, `uv.lock`, реального `.env.local` с локальными значениями, наполнение заглушек use case'ов и адаптеров рабочим кодом, настройка CI, написание тестов в `tests/`.
