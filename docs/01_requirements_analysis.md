# Анализ требований — MVP персонального AI-ассистента «Декодер»

> **Статус: Недействителен.** Документ заменён версией 2.0 — см. [`docs/versions/01_requirements_analysis_v2.0.md`](versions/01_requirements_analysis_v2.0.md).

## 1. Назначение системы

«Декодер» — персональный AI-ассистент, работающий в мессенджере Telegram через Telegram Bot API. Система ведёт многошаговый диалог с пользователем, учитывает историю общения, применяет заданный профиль автора (его стиль изложения и ограничения) и формирует ответы на основе документов заказчика, найденных через семантический поиск (RAG, Retrieval-Augmented Generation) в базе знаний.

Управление документами и кейсами выполняется администратором через отдельную панель. Все ключевые операции системы подлежат журналированию.

MVP закладывает модульную архитектуру с выделенными точками расширения, прежде всего для будущего аналитического модуля, не входящего в текущий состав.

## 2. Роли пользователей

### 2.1 Пользователь
Конечный получатель сервиса, взаимодействующий с ассистентом через Telegram-бота. Ведёт диалог, задаёт вопросы, может явной командой попросить сохранить о себе факт в долговременной памяти.

### 2.2 Администратор
Управляет составом базы знаний (документами) и кейсами через панель администратора. В MVP не имеет доступа к редактированию профиля автора и не управляет пользователями или их данными в сервисе памяти.

### 2.3 Автор (профильная сущность, не интерактивная роль)
Профиль автора — набор данных о стиле, тоне и ограничениях, которые ассистент применяет при формировании ответов. В MVP «автор» не является активной ролью, взаимодействующей с системой через интерфейс.

**Решение:** в MVP используется один общий профиль автора, применяемый ко всем пользователям ассистента. Профиль хранится в SQLite и первоначально загружается из конфигурационного файла или начальных данных базы (seed-данных). Редактирование профиля через панель администратора или иной интерфейс в MVP не реализуется — изменение профиля выполняется вне системы (например, прямым обновлением конфигурации или записи в базе).

## 3. Основные пользовательские сценарии

### Сценарии пользователя
1. Пользователь начинает диалог с ботом; ассистент отвечает с учётом профиля автора (стиль, ограничения).
2. Пользователь задаёт вопрос по теме, покрытой документами заказчика; ассистент находит релевантные фрагменты через RAG и формирует ответ на их основе.
3. Пользователь ведёт многошаговый диалог; ассистент учитывает предыдущие реплики в рамках диалога при формировании следующего ответа.
4. Пользователь отправляет команду `/запомнить <факт>`; ассистент показывает сформулированный факт и запрашивает подтверждение (нажатием кнопки «Сохранить» или явным ответом пользователя); факт сохраняется в сервисе памяти только после подтверждения.
5. Пользователь возвращается к диалогу позже; ассистент учитывает ранее подтверждённые факты при формировании ответа.
6. Пользователь отправляет команду `/память`, чтобы просмотреть список сохранённых о нём фактов.
7. Пользователь отправляет команду `/забыть`, чтобы удалить ранее сохранённый факт.

### Сценарии администратора
8. Администратор добавляет, обновляет или удаляет документ в базе знаний через панель администратора.
9. Администратор создаёт, просматривает или архивирует кейс через панель администратора. Кейс — структурированный пример выполнения пользовательской задачи (исходные данные, тип задачи, ожидаемый подход, пример результата), а не клиентский проект и не отдельная база знаний.
10. Администратор может связать документ с кейсом; такая связь используется как дополнительный пример при формировании ответа и не ограничивает доступ пользователей к остальной базе знаний.

Просмотр журналов работы системы через панель администратора не входит в очерченные сценарии, поскольку панель администратора ограничена управлением документами и кейсами (см. раздел 6).

## 4. Функциональные требования

### 4.1 Telegram-бот
- Принимает текстовые сообщения пользователя через Telegram Bot API и передаёт их в AI Core (ядро ИИ).
- Возвращает пользователю сформированный ответ.
- Поддерживает многошаговый диалог в рамках переписки с конкретным пользователем.
- Распознаёт и передаёт в AI Core явную команду пользователя на сохранение факта в память.

### 4.2 AI Core
- Принимает входящее сообщение пользователя и данные о контексте диалога.
- Запрашивает у сервиса профиля актуальный профиль автора (стиль, ограничения).
- Запрашивает у сервиса памяти подтверждённые факты о пользователе, применимые к диалогу.
- Запрашивает у сервиса поиска релевантные фрагменты документов и кейсов из базы знаний.
- Формирует единый контекст запроса, объединяя источники в следующем порядке приоритета:
  1. системные ограничения и требования безопасности;
  2. профиль автора;
  3. документы базы знаний (включая связанные кейсы);
  4. подтверждённые пользовательские факты;
  5. история текущего диалога;
  6. общие знания языковой модели.
- Профиль автора определяет форму и стиль ответа, но не может изменять фактическое содержание, взятое из документов базы знаний.
- Направляет сформированный контекст активному поставщику языковой модели через LLM Adapter (адаптер языковой модели), выбранный конфигурацией (переменными окружения); в рамках одного запроса к другим поставщикам не обращается.
- Фиксирует в журнале использованного поставщика и модель для каждого вызова.
- Возвращает сформированный ответ Telegram-боту.
- Выступает точкой расширения для будущего аналитического модуля.

### 4.3 Сервис профиля
- Хранит и предоставляет AI Core единый профиль автора: стиль изложения, ограничения на содержание ответов. Профиль общий для всех пользователей ассистента.
- Профиль хранится в SQLite и первоначально загружается из конфигурационного файла или начальных данных базы.
- Редактирование профиля через панель администратора или иной пользовательский интерфейс в MVP не предусмотрено.

### 4.4 Сервис памяти
- Разграничивает два вида данных:
  - **История диалога** — сообщения пользователя и ассистента, необходимые для продолжения текущего разговора. При формировании ответа используется ограниченное окно последних сообщений либо краткое резюме диалога. История не считается обучением и автоматически не преобразуется в долговременные факты.
  - **Долговременная память** — только отдельные факты, явно сохранённые пользователем.
- Сохраняет факт о пользователе только после команды `/запомнить <факт>` и последующего подтверждения пользователем (кнопка «Сохранить» или явный ответ); без подтверждения факт не сохраняется.
- Предоставляет по команде `/память` список ранее сохранённых фактов пользователя.
- Удаляет факт по команде `/забыть`.
- Предоставляет AI Core подтверждённые факты для использования в текущем диалоге.
- Не выполняет автоматическое извлечение или сохранение фактов из переписки без явной команды и подтверждения.

### 4.5 Сервис поиска по базе знаний (RAG)
- Принимает запрос от AI Core и выполняет семантический поиск релевантных фрагментов документов в базе знаний.
- Возвращает найденные фрагменты AI Core для использования в формировании ответа.

### 4.6 База знаний
- Хранит документы заказчика и кейсы в форме, пригодной для семантического поиска. Оригинальные документы хранятся в файловом хранилище; их метаданные (название, категория, метки, связь с кейсом) — в SQLite; фрагменты, векторы и поисковые метаданные — в Qdrant.
- База знаний едина для всех пользователей ассистента. Категории и метки у документов и кейсов допускаются, но разграничение доступа по пользователям или клиентам в MVP не реализуется.
- Обновляется исключительно через панель администратора.

### 4.7 Панель администратора
- Позволяет администратору добавлять, изменять и удалять документы в базе знаний.
- Позволяет администратору создавать, просматривать, изменять и архивировать кейсы (структурированные примеры выполнения задач) и связывать их с документами.
- Не предоставляет функций редактирования профиля автора.
- Не предоставляет функций управления пользователями или их данными в сервисе памяти.
- Использует одну административную учётную запись: логин и хеш пароля задаются через переменные окружения и не хранятся в SQLite; административные маршруты защищаются сессией. Полноценная система ролей и управления несколькими администраторами в MVP не создаётся.

### 4.8 Журналирование
Ведение журналов разделяется на три вида, каждый со своим способом хранения:
- **Технические журналы** — ошибки, продолжительность операций, состояние интеграций с внешними поставщиками моделей. Выводятся приложением в структурированном виде в stdout/stderr; в локальной среде их собирает Docker, в Yandex Cloud — штатная система сбора журналов контейнеров. Ошибки, требующие последующего анализа, дополнительно записываются в таблицу системных событий/ошибок в SQLite.
- **Аудит действий администратора** — загрузка, изменение и удаление документов и кейсов; хранится в отдельной таблице SQLite.
- **История диалогов** — хранится в отдельных таблицах SQLite, а не как обычные журналы приложения.

Такой подход не требует отдельного сервиса журналирования в MVP.

Технические журналы и аудит фиксируют факт обработки запроса, технические параметры операции и обезличенные идентификаторы, не сохраняя чувствительное содержание. В журналы не помещаются: ключи API, пароли, полный текст пользовательских фактов, полные запросы к модели без необходимости, содержимое документов, токены Telegram, персональные данные в открытом виде.

## 5. Нефункциональные требования

- **Язык интерфейса и ответов** — русский как основной.
- **Конфиденциальность данных** — документы заказчика и данные пользователей (включая сохранённые факты) не должны становиться доступны сторонним пользователям системы.
- **Разграничение доступа** — операции администратора (управление документами и кейсами) должны быть недоступны обычным пользователям.
- **Модульность** — компоненты системы (AI Core, сервис профиля, сервис памяти, сервис поиска, база знаний, панель администратора, журналирование) должны быть выделены как самостоятельные модули с чётко очерченными точками взаимодействия, обеспечивающими последующее подключение аналитического модуля без переработки существующих компонентов.
- **Возможность смены поставщика языковой модели** — активный поставщик (YandexGPT или OpenAI API) и конкретная модель задаются конфигурацией (переменными окружения) и изменяются без правки программного кода.
- **Развёртывание** — система должна разворачиваться в контейнерах (Docker) в среде Yandex Cloud.
- **Нагрузка (проектное допущение).** Заказчик количественные требования не зафиксировал. Для MVP принято рабочее допущение: до 100 зарегистрированных пользователей, до 10 одновременных активных диалогов, база знаний до 1 000 документов или до 100 000 фрагментов, без требований высокой доступности. Это не договорная гарантия, а допущение, необходимое для выбора SQLite, одного экземпляра приложения и простой конфигурации Qdrant. Горизонтальное масштабирование не является целью MVP; см. риск в разделе 9.
- **Время отклика (ориентир).** Типичный ответ без обращения к языковой модели — до 2 секунд; ответ с использованием RAG и языковой модели — целевой диапазон 15–30 секунд.
- **Индексация документов** выполняется асинхронно и не блокирует работу бота.

## 6. Границы MVP

В состав MVP входят:
1. Telegram-бот на основе Telegram Bot API.
2. AI Core — центральный модуль обработки и маршрутизации запросов.
3. Сервис профиля (хранение и предоставление профиля автора).
4. Сервис памяти (хранение фактов, сохраняемых только по явной команде пользователя).
5. Сервис поиска по базе знаний с использованием RAG.
6. База знаний, хранящая документы заказчика.
7. Панель администратора для управления документами и кейсами.
8. Журналирование ключевых операций системы.

Технологический стек ограничен: Python, FastAPI, Telegram Bot API, YandexGPT и OpenAI API (подключаются через LLM Adapter, активный выбирается конфигурацией), Qdrant, SQLite, LangChain (только при обоснованном упрощении реализации), Docker, Yandex Cloud.

## 7. Функции, отложенные на следующие этапы

- Голосовой интерфейс.
- Аналитический модуль.
- Веб-интерфейс пользователя.
- Интеграции с внешними сервисами (помимо Telegram Bot API и используемых языковых моделей).
- Автоматическое обучение системы на переписке пользователей.
- Редактирование профиля автора через панель администратора.
- Управление пользователями и их данными через панель администратора.

## 8. Архитектурные ограничения

- Реализация выполняется на Python с использованием FastAPI для серверной части.
- Взаимодействие с пользователем — исключительно через Telegram Bot API; иные каналы связи в MVP не предусмотрены.
- В MVP реализуются два LLM Adapter — для YandexGPT и для OpenAI API, реализующие единый интерфейс для AI Core. Активный поставщик и конкретная модель задаются переменными окружения; переключение между ними выполняется изменением конфигурации, без изменения программного кода. Автоматическое переключение между поставщиками во время работы (например, при недоступности активного поставщика) в MVP не реализуется. Каждый вызов модели фиксирует использованного поставщика и модель.
- **Dependency Inversion Principle** (принцип инверсии зависимостей) — бизнес-логика (AI Core и остальные сервисы) не должна зависеть от инфраструктурных компонентов (Telegram, SQLite, Qdrant, YandexGPT, OpenAI API). Все внешние зависимости подключаются через интерфейсы (адаптеры, включая LLM Adapter).
- Qdrant используется как векторное хранилище: хранит фрагменты документов, векторы и поисковые метаданные для сервиса поиска по базе знаний.
- SQLite используется как хранилище структурированных данных: профиль автора, метаданные документов и кейсов, аудит действий администратора, история диалогов, системные события/ошибки, требующие анализа. Учётные данные администратора (логин и хеш пароля) в SQLite не хранятся — задаются через переменные окружения.
- Оригинальные файлы документов хранятся в файловом хранилище в составе базы знаний.
- Технические журналы приложение выводит в stdout/stderr; их сбор в локальной среде выполняет Docker, а в Yandex Cloud — штатная система сбора журналов контейнеров.
- LangChain допускается к использованию только там, где он действительно упрощает реализацию, а не как обязательный элемент стека.
- Развёртывание — контейнеризация через Docker с размещением в Yandex Cloud.
- Архитектура должна предусматривать точки расширения для аналитического модуля, не реализуя его функциональность в MVP.
- Сохранение пользовательских фактов реализуется только как реакция на явную команду; фоновое или автоматическое извлечение фактов из переписки в архитектуре не допускается.

## 9. Риски и неоднозначные требования

Большая часть ранее выявленных неоднозначностей закрыта архитектурными решениями (см. разделы 2–5 и 8): единый профиль автора, определение кейса, граница истории и памяти, команды `/запомнить`, `/память`, `/забыть` с подтверждением, выбор поставщика языковой модели через LLM Adapter (YandexGPT, OpenAI API) и конфигурацию, единая база знаний без разграничения доступа, единая учётная запись администратора (учётные данные — только в переменных окружения), разделение и место хранения журналов (технические — stdout/stderr и сборщик логов контейнеров, аудит и история диалогов — таблицы SQLite).

Оставшиеся риски:

- **Отсутствие рантайм-переключения между поставщиками модели.** Поскольку активный поставщик задаётся конфигурацией и переключается только её изменением (без автоматического перехода на резервный LLM Adapter при сбое), недоступность выбранного поставщика во время работы приведёт к отказу в обработке запросов, пока конфигурация не будет обновлена и сервис не перезапущен.
- **Количественные допущения не подтверждены заказчиком.** Принятые для MVP ориентиры нагрузки (до 100 пользователей, до 10 одновременных диалогов, до 1 000 документов / 100 000 фрагментов) и времени ответа (до 2 секунд без обращения к модели, 15–30 секунд с RAG и языковой моделью) — проектные допущения архитектора, а не согласованные с заказчиком договорные требования. Они определяют выбор SQLite, одного экземпляра приложения и простой конфигурации Qdrant. Если фактическая нагрузка их превысит, потребуется пересмотр архитектуры (более производительная СУБД, горизонтальное масштабирование, отдельная очередь для индексации).
- **Единый профиль и единая база знаний как принятое упрощение.** Решение обслуживать всех пользователей одним общим профилем автора и одной неразделённой базой знаний соответствует текущему объёму MVP, но при появлении нескольких авторов или клиентов с изолированными данными потребует пересмотра сервиса профиля и модели доступа к базе знаний.
- **Единая учётная запись администратора.** Отсутствие системы ролей упрощает MVP, но означает, что при необходимости нескольких администраторов с разными правами потребуется отдельная доработка модели доступа панели.

## 10. Вопросы, требующие архитектурного решения

На текущем этапе все ранее выявленные вопросы получили рабочее решение (см. разделы 2–5 и 8). Открытых вопросов, блокирующих переход к проектированию архитектуры, не осталось.

Перед фиксацией итоговой архитектуры рекомендуется подтвердить с заказчиком количественные допущения о нагрузке и времени ответа (раздел 9) — при существенном расхождении с реальными ожиданиями они могут повлиять на выбор СУБД и схему развёртывания.
