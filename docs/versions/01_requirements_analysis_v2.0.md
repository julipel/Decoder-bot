# Анализ требований — MVP персонального AI-ассистента «Декодер»

**Версия документа:** 2.0
**Статус:** Approved
**Дата изменения:** 2026-07-28
**Предыдущая версия:** [`docs/01_requirements_analysis.md`](../01_requirements_analysis.md) (версия 1.0)
**Причина изменения:** расширение и уточнение согласованного с заказчиком состава MVP — переход от единого профиля автора и генерации без выбора модели/сценария к нескольким профилям автора, генерации контента через выбираемые Content Skills, выбору типа контента, каталогу моделей и Prompt Engine.

Документ является новой редакцией анализа бизнес- и функциональных требований. Он не описывает системную архитектуру, физическую модель базы данных, программные интерфейсы (API) или структуру классов реализации — эти вопросы остаются предметом последующих проектных документов (`docs/02` и далее), которые будут пересмотрены отдельно вслед за этой редакцией требований.

## 1. Назначение системы

«Декодер» — персональный AI-ассистент для создания контента и работы с информацией, работающий в мессенджере Telegram через Telegram Bot API.

В основе системы лежит универсальный сценарий обработки пользовательского запроса (раздел 4.2): одна и та же общая схема применяется к выполнению разных AI-задач — генерации текста, генерации изображения и формированию ответа по базе знаний. В рамках этого сценария система решает две связанные бизнес-задачи:
- помогает пользователю создавать контент под собственный авторский стиль и конкретную задачу;
- отвечает на вопросы пользователя с опорой на базу знаний заказчика через семантический поиск (RAG, Retrieval-Augmented Generation).

Для выполнения AI-задачи по генерации контента система должна:
- вести многошаговый диалог с пользователем;
- позволять пользователю создавать и выбирать один из нескольких собственных профилей автора (`Author Profile`);
- позволять выбирать тип контента;
- позволять выбирать Content Skill, совместимый с выбранным типом контента;
- позволять выбирать конкретную модель из каталога моделей либо режим «Автоматически»;
- формировать итоговую инструкцию для модели через Prompt Engine на основе профиля автора, выбранного Skill, типа контента, исходных данных пользователя, RAG-контекста и подтверждённой памяти;
- учитывать RAG-контекст там, где это предусмотрено выбранным Skill или запросом пользователя;
- учитывать подтверждённые факты долговременной памяти пользователя;
- возвращать пользователю готовый результат генерации.

Управление документами и кейсами базы знаний выполняется администратором через отдельную панель. Все ключевые операции системы подлежат журналированию.

Аналитический модуль, мониторинг конкурентов и автоматический сбор внешних данных (социальные сети, видеохостинги, CRM и подобные источники) не входят в состав MVP. MVP закладывает модульную архитектуру с точками расширения для будущего аналитического модуля, не реализуя его функциональность.

## 2. Роли пользователей

### 2.1 Пользователь

Конечный получатель сервиса, взаимодействующий с ассистентом через Telegram-бота. Ведёт диалог, создаёт и выбирает собственные профили автора, запускает генерацию контента, задаёт вопросы по базе знаний, может явной командой попросить сохранить о себе факт в долговременной памяти.

### 2.2 Администратор

Администратор управляет составом базы знаний (документами) и кейсами через панель администратора. Администратор не управляет профилями авторов пользователей, не управляет памятью пользователей, не редактирует каталог Content Skills и не редактирует каталог моделей.

Каталог Content Skills и каталог моделей в MVP не редактируются через интерфейс — они загружаются из конфигурации или seed-данных (см. разделы 4.5, 4.7). Административный редактор Skills и административный редактор каталога моделей не входят в MVP.

### 2.3 Профиль автора (`Author Profile`) — не интерактивная роль

Профиль автора — набор данных о стиле, тоне, нише и ограничениях, которые ассистент применяет при формировании контента для конкретного пользователя. Профиль автора не является активной ролью, взаимодействующей с системой через интерфейс, — это данные, которые пользователь создаёт и выбирает, а не отдельный субъект действия.

Правила работы с профилями автора:

- пользователь может иметь несколько собственных профилей автора; по умолчанию одному пользователю разрешено до четырёх активных (неархивных) профилей автора одновременно — это ограничение может быть изменено конфигурацией системы без изменения настоящего документа (раздел 9);
- архивные профили не учитываются в этом лимите — количество архивных профилей у пользователя не ограничено;
- профили автора изолированы между пользователями — пользователь не имеет доступа к чужим профилям ни на чтение, ни на изменение;
- профиль выбирается пользователем перед генерацией контента;
- у пользователя может существовать активный профиль по умолчанию, который система предлагает при генерации без явного выбора другого профиля;
- пользователь может создать, просмотреть, изменить и архивировать собственный профиль через Telegram-интерфейс;
- удаление профиля в MVP не предусмотрено — вместо физического удаления профиль архивируется; архивный профиль сохраняется, но недоступен для выбора при новой генерации.

### 2.4 Идентификация пользователя

Пользователь идентифицируется системой по Telegram User ID. Отдельная регистрация пользователей (собственный логин, пароль или иной идентификатор, не связанный с Telegram) в MVP отсутствует.

Все данные, принадлежащие пользователю, — профили автора, долговременная память, история диалога и состояние текущего сценария генерации — связываются с его Telegram User ID.

## 3. Основные пользовательские сценарии

### Сценарии профиля автора

1. Пользователь просматривает список собственных профилей автора.
2. Пользователь создаёт новый профиль автора через пошаговый мастер в Telegram.
3. Пользователь редактирует существующий собственный профиль автора.
4. Пользователь выбирает активный профиль автора (используемый по умолчанию при генерации).
5. Пользователь архивирует профиль автора, который больше не использует.

### Сценарии генерации контента

6. Пользователь начинает сценарий создания контента.
7. Пользователь выбирает тип контента.
8. Пользователь выбирает Content Skill, совместимый с выбранным типом контента (и, при необходимости, с профилем).
9. Пользователь выбирает конкретную модель из каталога моделей либо режим «Автоматически».
10. Пользователь вводит исходные данные, требуемые выбранным Skill.
11. Система формирует итоговый запрос к модели через Prompt Engine на основе профиля, Skill, типа контента, исходных данных, RAG-контекста и подтверждённой памяти.
12. Пользователь получает результат генерации.
13. Пользователь запускает повторную генерацию текущего результата по собственному явному действию (правило раздела 9: каждая повторная генерация считается новой операцией обработки запроса; если пользователь не изменил профиль, Skill, тип контента, модель или исходные данные, повторная генерация использует параметры предыдущей операции, иначе начинается новый сценарий генерации).

### Сценарии базы знаний и диалога

14. Пользователь задаёт вопрос по теме, покрытой документами заказчика; ассистент находит релевантные фрагменты через RAG и формирует ответ на их основе.
15. Пользователь ведёт многошаговый диалог; ассистент учитывает предыдущие реплики в рамках диалога и текущего сценария при формировании следующего ответа.

### Сценарии памяти

16. Пользователь отправляет команду `/запомнить <факт>`; ассистент показывает сформулированный факт и запрашивает подтверждение (нажатием кнопки «Сохранить» или явным ответом пользователя); факт сохраняется в долговременной памяти только после подтверждения.
17. Пользователь отправляет команду `/память`, чтобы просмотреть список сохранённых о нём фактов, и может удалить факт командой `/забыть`.

### Сценарии администратора

18. Администратор добавляет, обновляет или удаляет документ в базе знаний через панель администратора.
19. Администратор создаёт, просматривает или архивирует кейс через панель администратора. Кейс — структурированный пример выполнения пользовательской задачи (исходные данные, тип задачи, ожидаемый подход, пример результата), а не клиентский проект и не отдельная база знаний.
20. Администратор может связать документ с кейсом; такая связь используется как дополнительный пример при формировании ответа/контента и не ограничивает доступ пользователей к остальной базе знаний.

### Сценарии управления сценарием и состоянием диалога

21. Пользователь отменяет текущий сценарий (создание/редактирование профиля, генерацию контента) на любом промежуточном шаге.
22. Пользователь возвращается в главное меню из любого текущего сценария.
23. Пользователь сбрасывает незавершённую генерацию и начинает новую.
24. Пользователь взаимодействует с элементом интерфейса, относящимся к уже неактуальному состоянию сценария (например, нажимает устаревшую inline-кнопку прошлого шага); система распознаёт устаревшее состояние и предлагает актуальное действие вместо ошибки без объяснения.

Просмотр журналов работы системы через панель администратора не входит в очерченные сценарии — панель администратора по-прежнему ограничена управлением документами и кейсами (см. раздел 6).

## 4. Функциональные требования

### 4.1 Telegram-интерфейс

Telegram-интерфейс — единственный канал взаимодействия пользователя с системой в MVP. Он не содержит бизнес-логики: любое пользовательское действие транслируется в вызов AI Core, а результат — в Telegram-разметку ответа.

Telegram-интерфейс должен поддерживать:
- главное меню;
- раздел профилей автора (список, создание, просмотр, редактирование, архивирование);
- пошаговый мастер создания профиля автора;
- выбор активного профиля при генерации;
- выбор типа контента;
- выбор Content Skill среди совместимых с выбранным типом контента;
- выбор модели из каталога либо режима «Автоматически»;
- ввод исходных данных, запрашиваемых выбранным Skill;
- запуск генерации;
- отображение результата генерации;
- понятную для пользователя обработку ошибок (без технических подробностей);
- команды долговременной памяти (`/запомнить`, `/память`, `/забыть`) и подтверждение сохранения факта;
- отмену текущего сценария на любом промежуточном шаге;
- возврат в главное меню из любого текущего сценария;
- сброс незавершённой генерации и начало новой;
- обработку устаревшего состояния сценария (например, нажатие пользователем inline-кнопки, относящейся к уже неактуальному шагу) — понятным для пользователя предложением актуального действия, а не отказом без объяснения.

### 4.2 AI Core

AI Core — центральный модуль обработки и маршрутизации запросов, реализующий единый универсальный сценарий обработки пользовательского запроса независимо от конкретной AI-задачи (генерация текста, генерация изображения или ответ по базе знаний). AI Core должен:
- принимать входящее пользовательское действие (сообщение, команду или выбор в интерфейсе) и данные о контексте диалога;
- определять, к какому пользовательскому сценарию относится действие (генерация контента, вопрос по базе знаний, управление профилем, управление памятью);
- запрашивать у сервиса профилей автора выбранный (или активный по умолчанию) профиль;
- запрашивать выбранный Content Skill;
- получать выбранный пользователем тип контента;
- получать выбранную пользователем модель либо признак режима «Автоматически»;
- перед выполнением генерации проверять: принадлежность выбранного профиля текущему пользователю; что выбранный профиль не архивирован; совместимость выбранного Skill с выбранным типом контента; совместимость выбранной (или автоматически подобранной) модели с выбранным Skill и его модальностью (раздел 4.6, раздел 9);
- отклонять любую несовместимую комбинацию с понятным пользователю сообщением, не пытаясь исполнить её частично;
- запрашивать у сервиса поиска RAG-контекст, когда это требуется выбранным Skill или характером запроса;
- запрашивать у сервиса памяти подтверждённые факты о пользователе, применимые к текущему сценарию;
- передавать профиль, Skill, тип контента, исходные данные пользователя, RAG-контекст и подтверждённую память в Prompt Engine для формирования итоговой инструкции;
- передавать итоговую инструкцию выбранной (или автоматически подобранной) модели через единый абстрактный интерфейс подключения моделей;
- возвращать пользователю сформированный результат;
- журналировать технические параметры каждой операции: фактически использованные провайдера и модель, использование RAG, продолжительность, статус и другие параметры раздела 4.12 — без чувствительного содержания.

AI Core не хранит профили автора, Skills, модели или документы базы знаний самостоятельно — это ответственность соответствующих сервисов, к которым AI Core обращается. AI Core выступает точкой расширения для будущего аналитического модуля.

### 4.3 Сервис профилей автора (Author Profile Service)

Сервис профилей автора обеспечивает:
- создание профиля автора;
- получение профиля по идентификатору;
- получение списка профилей автора конкретного пользователя;
- изменение существующего профиля;
- назначение одного из профилей активным по умолчанию для пользователя;
- архивирование профиля (замена операции удаления, раздел 2.3);
- проверку принадлежности профиля пользователю перед любым чтением или изменением;
- запрет на использование архивного или принадлежащего другому пользователю профиля при генерации;
- ограничение числа активных профилей одного пользователя — по умолчанию не более четырёх, значение управляется конфигурацией системы (раздел 2.3, раздел 9); архивные профили в это ограничение не входят.

Профиль автора должен содержать на бизнес-уровне (без фиксации физических типов полей или структуры хранения):
- название профиля;
- нишу или тематику;
- целевую аудиторию;
- позиционирование;
- тон и стиль изложения;
- предпочитаемую лексику;
- нежелательную лексику;
- предпочтительные приёмы изложения;
- запрещённые приёмы изложения;
- правила форматирования результата;
- примеры текстов автора — опционально; вводятся пользователем как обычный текст непосредственно через Telegram; загрузка файлов с примерами текстов в MVP не поддерживается (раздел 9);
- статус (действующий/архивный).

Профиль определяет форму, стиль и ограничения контента, но не может подменять фактическое содержание, взятое из документов базы знаний.

### 4.4 Мультимодальная генерация контента

Генерация контента — один из вариантов универсального сценария обработки пользовательского запроса (раздел 1, раздел 4.2), реализуемый теми же шагами, что и формирование ответа по базе знаний. MVP поддерживает генерацию контента в двух модальностях (раздел 4.6): **TEXT** и **IMAGE**. Генерация выполняется для двух типов результата — текста и изображения; изображение является полноценным, самостоятельным результатом работы системы, а не вспомогательным материалом.

Архитектура генерации едина для обеих модальностей — различается только используемая модель, подключаемая на последнем шаге:

```
Author Profile
   ↓
Content Skill
   ↓
Generation Type
   ↓
Model
   ↓
Prompt Engine
   ↓
Generation
```

Пользовательские результаты, поддерживаемые в MVP:
- статья (TEXT);
- пост (TEXT);
- сценарий (TEXT);
- описание (TEXT);
- контент-план (TEXT);
- идеи (TEXT);
- изображение (IMAGE).

Промпт для изображения может формироваться и использоваться Prompt Engine внутренне как промежуточный шаг перед обращением к модели генерации изображений, но конечным результатом, который получает пользователь по Skill модальности IMAGE, является готовое изображение, а не текстовое описание к нему.

Иные текстовые форматы, явно предусмотренные утверждёнными Content Skills, также входят в MVP при условии их отнесения к модальности TEXT (раздел 4.5).

Видео, аудио, презентации и иные документные форматы в MVP не входят (раздел 7). Конкретные API или инструменты генерации изображений этот документ не описывает — их выбор относится к системной архитектуре.

### 4.5 Content Skills

Content Skill (далее — Skill) — специализированный конфигурируемый сценарий генерации контента. Skill не является автономным AI-агентом и не принимает самостоятельных решений вне заданной конфигурации — он определяет параметры и правила, по которым AI Core и Prompt Engine формируют запрос к модели.

Skill определяет:
- назначение;
- поддерживаемую модальность (TEXT или IMAGE — раздел 4.6);
- поддерживаемый тип (типы) контента в рамках этой модальности;
- требуемые исходные данные, запрашиваемые у пользователя;
- шаблон или правила формирования запроса к модели;
- требования к результату;
- совместимость с моделями каталога;
- режим использования RAG (обязательное, опциональное или отключённое использование — раздел 4.9);
- возможность использования долговременной памяти пользователя (раздел 4.10);
- статус доступности.

Примеры Skills (перечень иллюстрирует тип Skill, а не конкретную площадку публикации, и не ограничивает окончательный каталог, раздел 9):
- Социальный пост → модальность TEXT;
- Длинная статья → модальность TEXT;
- Иллюстрация продукта → модальность IMAGE;
- Маркетинговый баннер → модальность IMAGE.

Правила использования каталога Skills:
- Skills выбираются пользователем на этапе генерации контента;
- пользователю показываются только Skills, совместимые с ранее выбранным типом контента и его модальностью;
- каталог Skills загружается из конфигурации или seed-данных, а не создаётся через пользовательский интерфейс;
- создание и редактирование Skills пользователем не поддерживается;
- редактор Skills в панели администратора не входит в MVP;
- каждый Skill из утверждённого каталога должен быть протестирован отдельно перед включением в состав MVP.

Точное число и окончательный состав Skills, входящих в каталог MVP, не фиксируются этим документом как исчерпывающий перечень — окончательный каталог Skills утверждается и поддерживается конфигурацией/seed-данными отдельно от анализа требований (раздел 9).

### 4.6 Выбор типа контента (Generation Type)

Система различает два связанных, но разных понятия:
- **пользовательский формат результата** — то, что пользователь выбирает и видит (например, «статья», «пост», «сценарий», «изображение»);
- **Generation Type (модальность)** — техническая характеристика, по которой система сопоставляет формат с совместимыми Skills и моделями.

MVP поддерживает ровно две модальности:

```
TEXT
IMAGE
```

Архитектура требований допускает последующее расширение перечня модальностей без изменения общей модели обработки пользовательского запроса (раздел 4.2). Это не расширяет состав MVP: иные модальности (в частности, видео и аудио) в MVP не входят и этим документом не поддерживаются (раздел 7).

Правила:
- тип контента, выбранный пользователем, однозначно определяет модальность (TEXT или IMAGE);
- модальность определяет набор доступных для выбора Skills — пользователю показываются только Skills, поддерживающие выбранную модальность;
- модальность определяет набор совместимых моделей — пользователю показываются только модели каталога, поддерживающие выбранную модальность (и, если применимо, конкретный Skill).

Система должна:
- показывать пользователю доступные типы контента;
- на основе выбранного типа контента (и его модальности) фильтровать список доступных для выбора Skills;
- на основе выбранного типа контента, модальности и Skill фильтровать список доступных для выбора моделей;
- отклонять несовместимые комбинации типа контента, Skill и модели с понятным сообщением пользователю, не выполняя генерацию по несовместимой комбинации.

### 4.7 Каталог моделей (Model Catalog)

Система ведёт каталог разрешённых моделей (Model Catalog). Выбор модели выполняется на уровне отдельного запроса пользователя, а не фиксируется конфигурацией всего экземпляра приложения при старте. Для каждой модели каталог содержит:
- понятное отображаемое имя, показываемое пользователю;
- провайдера;
- технический идентификатор модели;
- поддерживаемые типы контента;
- статус доступности;
- признак доступности данной модели пользователю.

Пользователь выбирает конкретную модель из каталога для отдельной генерации либо выбирает режим «Автоматически». Пользователю не обязательно показывать конкретные, быстро устаревающие технические версии моделей, если это не требуется для понимания выбора, — отображаемое имя может абстрагироваться от версии.

Режим «Автоматически» входит в MVP. В этом режиме система выбирает первую совместимую модель из приоритетного списка, заданного конфигурацией каталога (совместимую с выбранной модальностью, типом контента и Skill), — без интеллектуальной маршрутизации: сложная оптимизация выбора модели по цене, качеству и скорости не входит в MVP (раздел 9).

Автоматический fallback на другую модель при отказе выбранной модели не входит в MVP. При недоступности выбранной модели система должна показать пользователю понятную ошибку без технических подробностей и предложить выбрать другую модель или тип действия.

Каждый вызов модели должен фиксировать в техническом журнале фактически использованные провайдера и модель — независимо от того, была ли модель выбрана пользователем явно или автоматически.

### 4.8 Prompt Engine

Prompt Engine — мультимодальный компонент: он формирует итоговую инструкцию как для текстовых моделей (модальность TEXT), так и для моделей генерации изображений (модальность IMAGE). Алгоритм формирования контекста и порядок приоритета источников одинаковы для обеих модальностей — различается только формат итогового запроса, передаваемого модели (структура текстовой инструкции против структуры запроса генерации изображения). Отдельный Image Prompt Engine как самостоятельный компонент не вводится.

Prompt Engine формирует итоговую инструкцию для модели, объединяя источники в следующем порядке приоритета:
1. системные ограничения и требования безопасности;
2. профиль автора (`Author Profile`);
3. выбранный Content Skill;
4. тип контента;
5. исходные данные, введённые пользователем;
6. RAG-контекст;
7. подтверждённая долговременная память;
8. необходимая история текущего пользовательского сценария (в пределах генерации или диалога).

Правила Prompt Engine:
- основа MVP — детерминированные шаблоны и правила, заданные Skills; Prompt Engine на этом уровне не принимает самостоятельных творческих решений, а применяет уже заданную конфигурацию;
- отдельный вызов вспомогательной модели для улучшения или переформулирования промпта (метамодели) не является обязательным элементом MVP;
- дополнительное улучшение промпта средствами модели может применяться только как опциональная, отдельно согласуемая стратегия для отдельных Skills, а не как обязательное поведение по умолчанию;
- Prompt Engine не выполняет психологический анализ аудитории сверх данных, явно предоставленных пользователем в профиле или исходных данных;
- Prompt Engine не гарантирует юридическую корректность формируемого или сгенерированного контента;
- итоговый внутренний промпт не обязан показываться пользователю;
- полный внутренний промпт не должен попадать в технические журналы (раздел 4.12).

Prompt Engine не зависит от Telegram и может использоваться любым будущим каналом взаимодействия, реализующим тот же входной контракт AI Core.

### 4.9 RAG (сервис поиска по базе знаний)

RAG используется не только для ответов на вопросы пользователя по базе знаний, но и при создании контента:
- для формирования ответов по базе знаний в рамках диалога;
- для создания фактически точного контента на основе документов заказчика;
- для использования брендбуков, продуктовых материалов, кейсов и примеров, хранящихся в базе знаний, при генерации контента.

Режим использования RAG определяется выбранным Content Skill, а не пользователем: пользователь не включает и не отключает RAG вручную ни для диалога, ни для отдельной генерации. Каждый Skill задаёт один из режимов:
- обязательное использование — генерация по такому Skill не выполняется без релевантного RAG-контекста, если он требуется по логике Skill;
- опциональное использование — RAG-контекст добавляется, если он найден, но не блокирует генерацию при его отсутствии;
- отключённое использование — Skill не обращается к RAG.

Для сценария вопроса по базе знаний вне генерации контента (раздел 3, сценарий 14) обращение к RAG выполняется системой автоматически, без отдельного пользовательского переключателя.

Система не должна подменять отсутствующие документы общими знаниями модели там, где Skill или запрос пользователя явно требует ответа или контента по базе знаний.

### 4.10 История и память

Система различает три самостоятельные сущности, которые не следует смешивать между собой. Ниже фиксируется только их бизнес-назначение и правила использования — способ их физического хранения выходит за рамки этого документа.

- **Dialogue History (история диалога)** — сообщения пользователя и ассистента, необходимые для продолжения текущего разговора, включая ответы на вопросы по базе знаний. История не считается обучением и автоматически не преобразуется в долговременные факты.
- **Generation Session State (состояние сессии генерации)** — текущий прогресс одного незавершённого сценария генерации контента (выбранный на данный момент профиль, тип контента, Skill, модель, введённые исходные данные, шаг мастера) или сценария создания/редактирования профиля. Существует только в пределах одного незавершённого сценария (раздел 3, сценарии 21–24) и не является ни историей диалога, ни долговременной памятью.
- **Long-term Memory (долговременная память)** — только отдельные факты о пользователе, явно сохранённые пользователем.

Результаты уже завершённой генерации контента остаются частью истории диалога (Dialogue History) — отдельная библиотека или архив созданного контента, независимый от истории диалога, в MVP не создаётся.

Правила использования долговременной памяти:
- долговременная память принадлежит пользователю (Telegram User ID, раздел 2.4), а не профилю автора; у пользователя одна память независимо от количества его профилей автора;
- смена активного профиля автора не изменяет и не очищает память пользователя;
- Content Skill может разрешать или запрещать использование долговременной памяти при генерации по этому Skill;
- результаты генерации контента не становятся фактами долговременной памяти автоматически ни при каких условиях;
- сохранение факта в долговременную память возможно только после явной команды `/запомнить <факт>` и последующего подтверждения пользователем (кнопка «Сохранить» или явный ответ) — без подтверждения факт не сохраняется.

Система предоставляет по команде `/память` список ранее сохранённых фактов пользователя и удаляет факт по команде `/забыть`.

### 4.11 Панель администратора

Функции панели администратора:
- добавление, изменение и удаление документов в базе знаний;
- создание, просмотр, изменение и архивирование кейсов, связывание их с документами.

В панель администратора в MVP не входят:
- управление профилями автора пользователей;
- управление долговременной памятью пользователей;
- редактор каталога Content Skills;
- редактор каталога моделей.

Каталог Content Skills и каталог моделей в MVP загружаются из конфигурации или seed-данных (разделы 4.5, 4.7), а не редактируются через панель администратора.

Панель администратора использует одну административную учётную запись: логин и хеш пароля задаются через переменные окружения и не хранятся в базе данных приложения; административные маршруты защищаются сессией.

### 4.12 Журналирование

Ведение журналов разделяется на технические журналы, аудит действий администратора и историю диалогов. Для операций генерации контента состав журналируемых параметров расширен по сравнению с обработкой обычного диалогового сообщения.

Для каждой операции генерации контента журналируются:
- обезличенный идентификатор пользователя;
- использованный профиль автора (идентификатор, не содержимое);
- использованный Content Skill;
- выбранный тип контента;
- выбранная пользователем модель (или признак режима «Автоматически»);
- фактически использованные провайдер и модель;
- факт использования RAG;
- продолжительность операции;
- статус операции;
- количество обращений к модели в рамках одной операции;
- тип ошибки, если операция завершилась неуспешно.

В технические журналы не помещаются:
- полный пользовательский запрос без необходимости;
- полный сформированный (итоговый) промпт;
- содержимое фактов долговременной памяти;
- содержимое документов базы знаний;
- ключи API, пароли, токены;
- персональные данные в открытом виде.

## 5. Нефункциональные требования

- **Язык интерфейса и ответов** — русский как основной.
- **Конфиденциальность данных** — документы заказчика, данные пользователей (профили автора, сохранённые факты памяти, история диалогов) не должны становиться доступны сторонним пользователям системы.
- **Изоляция профилей автора** — профили автора одного пользователя недоступны другому пользователю ни на чтение, ни на изменение (раздел 2.3).
- **Разграничение доступа** — операции администратора (управление документами и кейсами) должны быть недоступны обычным пользователям.
- **Проверка совместимости выбранных элементов** — перед выполнением генерации система обязана проверить принадлежность профиля пользователю, отсутствие у профиля статуса «архивный», совместимость Skill с типом контента и совместимость модели с выбранным Skill и модальностью (раздел 4.2, раздел 4.6); несовместимые комбинации отклоняются.
- **Выбор модели на уровне запроса** — выбор модели выполняется на уровне отдельного запроса пользователя (явно или через режим «Автоматически»), а не фиксируется конфигурацией всего экземпляра приложения на момент старта.
- **Управляемость каталога моделей** — каталог разрешённых для использования моделей управляется конфигурацией, а не жёстко зашивается в код.
- **Модульность.** В состав логических компонентов системы, выделенных с чёткими точками взаимодействия, входят: AI Core, Author Profile Service (сервис профилей автора), Content Skill Service (сервис Content Skills), Prompt Engine, Model Catalog (каталог моделей), Memory (сервис памяти), RAG/Search (сервис поиска), Knowledge Base (база знаний), Telegram Adapter (Telegram-интерфейс), Admin (панель администратора), Logging/Audit (журналирование). Перечисленные компоненты — логическое, не физическое разделение: MVP остаётся модульным монолитом, компоненты не являются отдельными микросервисами. Модульность должна обеспечивать последующее подключение аналитического модуля без переработки существующих компонентов.
- **Независимость от конкретного поставщика языковой модели** — набор допустимых моделей задаётся каталогом (раздел 4.7) и не ограничен конкретным списком поставщиков и не привязан к единственному активному поставщику всего экземпляра приложения.
- **Отсутствие логирования чувствительных данных** — полные промпты, содержимое документов, факты памяти и иные чувствительные данные не логируются (раздел 4.12).
- **Развёртывание** — система должна поддерживать контейнерное развёртывание в совместимой облачной инфраструктуре; конкретный облачный провайдер этим документом не фиксируется.
- **Нагрузка (проектное допущение).** Рабочее допущение по нагрузке: до 100 зарегистрированных пользователей, до 10 одновременных активных диалогов, база знаний до 1 000 документов или до 100 000 фрагментов. Расширение состава MVP (несколько профилей на пользователя, каталог моделей, каталог Skills) увеличивает объём данных и число операций на один пользовательский сценарий генерации, что учтено как риск в разделе 10, а не как пересмотренное числовое допущение.
- **Время отклика (ориентир, не гарантия).** Фактическое время отклика зависит от выбранной модели, объёма RAG-контекста и количества внешних вызовов модели в рамках одной операции (например, при использовании опциональной стратегии улучшения промпта, раздел 4.8). Единый числовой диапазон времени отклика не фиксируется как гарантия — время отклика остаётся проектным ориентиром для оценки архитектуры, а не договорным обязательством.
- **Индексация документов** выполняется асинхронно и не блокирует работу бота.

## 6. Границы MVP

В состав MVP версии 2.0 входят:

1. Telegram-интерфейс.
2. Несколько профилей автора на пользователя (по умолчанию до четырёх активных, значение конфигурируемо, раздел 2.3).
3. Создание, редактирование, выбор и архивирование профилей автора.
4. Мультимодальная генерация контента — текст (TEXT) и изображение (IMAGE).
5. Каталог Content Skills.
6. Выбор типа контента (Generation Type: TEXT/IMAGE).
7. Выбор модели из каталога или режим «Автоматически».
8. Prompt Engine.
9. RAG (сервис поиска по базе знаний).
10. История диалога.
11. Подтверждаемая долговременная память.
12. База знаний.
13. Панель администратора для документов и кейсов.
14. Журналирование.

Технологический стек: Python, FastAPI, Telegram Bot API, единый абстрактный слой доступа к языковым моделям и моделям генерации изображений (конкретная реализация шлюза определяется системной архитектурой, раздел 8), библиотеки оркестрации LLM определяются системной архитектурой, векторное хранилище для семантического поиска, хранилище структурированных данных, контейнерное развёртывание в совместимой облачной инфраструктуре.

## 7. Функции, отложенные на следующие этапы

За пределами MVP версии 2.0 остаются:

- мониторинг конкурентов;
- сбор данных из внешних источников (YouTube, Дзен, CRM, комментарии, социальные сети и подобные);
- аналитический движок (аналитический модуль);
- психологический анализ аудитории;
- автоматическое создание маркетинговых гипотез;
- A/B-тестирование;
- многоступенчатый self-correction loop (цикл автоматической самопроверки и исправления результата);
- автоматический внешний фактчекинг;
- юридическая экспертиза и гарантии соблюдения законодательства;
- голосовой интерфейс;
- генерация видео;
- генерация аудио;
- автоматическое обучение системы на переписке пользователей;
- пользовательский редактор Content Skills;
- административный редактор Content Skills;
- сложная маршрутизация выбора модели по цене, качеству и скорости;
- автоматический fallback при отказе модели, если он не будет отдельно согласован с заказчиком;
- веб-интерфейс пользователя.

Непосредственная генерация изображений входит в состав MVP (раздел 4.4, раздел 9) — за пределами MVP остаются только генерация видео и генерация аудио (см. выше).

## 8. Технические ограничения MVP

Ниже — ограничения, обязательные для последующего проектирования системной архитектуры.

- Реализация выполняется на Python с использованием FastAPI для серверной части.
- Взаимодействие с пользователем — исключительно через Telegram Bot API; иные каналы связи в MVP не предусмотрены.
- Бизнес-логика AI Core, Prompt Engine и остальных сервисов не должна зависеть от конкретного поставщика языковой модели или модели генерации изображений.
- Модели подключаются через единый абстрактный интерфейс (порт), не привязанный к конкретному поставщику; конкретные реализации регистрируются в каталоге моделей.
- Разрешённые к использованию модели задаются каталогом моделей (раздел 4.7), управляемым конфигурацией, а не жёстко ограниченным списком поставщиков в коде.
- Модель выбирается на уровне отдельного запроса — пользователем явно либо системой автоматически в режиме «Автоматически», а не фиксируется на весь экземпляр приложения при старте.
- Профили автора принадлежат пользователям и изолированы между ними (раздел 2.3, раздел 5).
- Content Skills задаются конфигурацией или seed-данными, а не создаются через пользовательский или административный интерфейс в MVP.
- Prompt Engine не зависит от Telegram и не содержит Telegram-специфичного кода.
- Система обязана валидировать совместимость выбранных пользователем элементов (профиль, Skill, тип контента, модель) перед выполнением генерации (раздел 4.2).
- MVP остаётся модульным монолитом — перечисленные в разделе 5 логические компоненты не выделяются в отдельные микросервисы.
- Аналитический модуль не реализуется в MVP; архитектура должна оставлять для него точку расширения.
- **Dependency Inversion Principle** — бизнес-логика (AI Core, Prompt Engine и остальные сервисы) не должна зависеть от инфраструктурных компонентов (Telegram, хранилище структурированных данных, векторное хранилище, конкретных поставщиков моделей). Все внешние зависимости подключаются через интерфейсы (адаптеры).
- Для сервиса поиска по базе знаний используется векторное хранилище; конкретная технология векторного хранилища определяется системной архитектурой.
- Для хранения структурированных данных (профили автора, метаданные документов и кейсов, аудит, история диалогов, факты памяти, системные события) используется реляционная база данных / хранилище структурированных данных; конкретная СУБД определяется системной архитектурой. Учётные данные администратора в этом хранилище не хранятся.
- Оригинальные файлы документов хранятся в файловом хранилище в составе базы знаний.
- Технические журналы приложение выводит в stdout/stderr.
- Развёртывание — система должна поддерживать контейнерное развёртывание в совместимой облачной инфраструктуре; конкретный облачный провайдер этим документом не фиксируется.
- Система использует единый абстрактный слой доступа к моделям. Конкретная реализация шлюза определяется системной архитектурой и может изменяться без изменения настоящего документа; бизнес-логика системы (AI Core, Prompt Engine, каталог моделей) от конкретной реализации шлюза не зависит и обращается к моделям только через этот абстрактный слой.

## 9. Принятые проектные решения и ограничения MVP

Этот раздел фиксирует окончательные решения по вопросам, детализирующим уже согласованный состав MVP версии 2.0. Документ требований полностью определяет границы MVP — открытых вопросов, требующих отдельного согласования с заказчиком до перехода к системной архитектуре, не остаётся.

1. **Модальности и типы контента.** MVP поддерживает ровно две модальности — TEXT и IMAGE. Исчерпывающий перечень пользовательских результатов зафиксирован в разделе 4.4: статья, пост, сценарий, описание, контент-план, идеи (модальность TEXT), изображение (модальность IMAGE), а также иные текстовые форматы, явно предусмотренные утверждёнными Content Skills.
2. **Генерация изображений.** Непосредственная генерация изображений (получение готового изображения) входит в состав MVP как самостоятельный, полноценный результат (раздел 4.4) — а не только подготовка текстового промпта для последующей внешней генерации.
3. **Окончательный список Content Skills.** Этим документом не перечисляется как исчерпывающий — состав каталога Skills утверждается и поддерживается конфигурацией/seed-данными отдельно от анализа требований (раздел 4.5). Документ фиксирует правила формирования и использования каталога, а не его точное содержимое.
4. **Объём каталога Skills.** Верхняя граница числа Skills не фиксируется как договорное требование; каталог управляется конфигурацией и может расширяться без пересмотра этого документа, при условии соблюдения правила раздела 4.5 (каждый Skill тестируется отдельно).
5. **Состав каталога моделей.** Конкретные модели, отображаемые пользователю на момент запуска MVP, определяются конфигурацией каталога моделей (раздел 4.7), а не перечисляются в этом документе.
6. **Единый слой доступа к моделям.** Система использует единый абстрактный слой доступа к моделям (раздел 8); конкретная реализация шлюза определяется системной архитектурой, бизнес-логика системы от неё не зависит, а замена реализации не требует пересмотра этого документа.
7. **Режим «Автоматически».** Входит в MVP как один из доступных пользователю вариантов выбора модели наравне с явным выбором конкретной модели (раздел 4.7); отдельного требования принудительно скрывать или отключать этот режим для части сценариев MVP не вводит.
8. **Количество профилей автора.** По умолчанию одному пользователю разрешено до четырёх активных профилей автора; архивные профили в лимит не входят. Это ограничение может быть изменено конфигурацией системы без изменения настоящего документа (раздел 2.3).
9. **Примеры текстов автора.** Вводятся пользователем как обычный текст непосредственно через Telegram; загрузка файлов в MVP не поддерживается (раздел 4.3).
10. **История созданного контента.** Отдельная библиотека или архив контента не создаётся — результаты генерации остаются частью истории диалога (Dialogue History, раздел 4.10).
11. **Включение RAG.** Пользователь не управляет использованием RAG вручную ни для диалога, ни для генерации — режим использования RAG полностью определяется выбранным Content Skill (раздел 4.9).
12. **Контроль лимитов и стоимости использования моделей.** Относится к эксплуатационному/биллинговому управлению системой, а не к бизнес-требованиям к функциональности MVP, и не блокирует границы MVP, зафиксированные в разделе 6.
13. **Исходные данные для конкретных Skills.** Общий перечень категорий исходных данных зафиксирован в разделе 4.5; конкретный набор полей для каждого отдельного Skill определяется конфигурацией этого Skill, а не перечисляется в этом документе целиком.
14. **Повторная генерация.** Каждая повторная генерация считается новой операцией обработки запроса (раздел 3, сценарий 13). Если пользователь не изменил профиль автора, Skill, тип контента, модель или исходные данные, повторная генерация использует параметры предыдущей операции. При изменении любого из этих параметров начинается новый сценарий генерации. Количественных ограничений на число повторных генераций документ не вводит.

## 10. Риски

Раздел фиксирует риски, актуальные для состава MVP версии 2.0. Профили автора изолированы на уровне пользователя (раздел 2.3), что снимает риски, связанные с общим профилем на всех пользователей, но не устраняет риски, связанные с самим расширением модели профилей (см. ниже).

- **Существенное расширение состава MVP.** Переход к нескольким профилям на пользователя, каталогу Skills, каталогу моделей, Prompt Engine и мультимодальной генерации (текст и изображения) увеличивает объём реализации и число взаимодействующих компонентов и, соответственно, риски сроков и тестирования.
- **Необходимость отдельного тестирования каждого Skill.** Поскольку каждый Skill определяет собственный шаблон формирования запроса и требования к результату, корректность одного Skill не гарантирует корректность другого — общее тестирование Prompt Engine недостаточно (раздел 4.5).
- **Неодинаковое поведение разных моделей на одном и том же Skill.** Одна и та же итоговая инструкция, сформированная Prompt Engine, может давать различный по качеству и структуре результат в зависимости от выбранной модели — риск не устраняется автоматической проверкой в MVP.
- **Изменение доступности и версий моделей у внешних поставщиков.** Модели в каталоге (раздел 4.7) могут становиться недоступными или заменяться поставщиком версией с иным поведением вне контроля системы; при отсутствии автоматического fallback (раздел 4.7) это приводит к отказу конкретных генераций до ручного обновления каталога.
- **Различия стоимости запросов между моделями.** Каталог моделей не фиксирует единую стоимость операции — выбор модели (в том числе автоматический) влияет на стоимость запроса; контроль лимитов и стоимости зафиксирован как вопрос вне рамок бизнес-требований к MVP (раздел 9, пункт 12), а не как техническое ограничение архитектуры.
- **Несовместимость типа контента, Skill и модели.** Ошибочная или устаревшая конфигурация каталога Skills/моделей может привести к формально доступному, но фактически несовместимому выбору; система обязана отклонять такие комбинации (раздел 4.2, раздел 4.6), но полнота проверки зависит от качества конфигурации, а не только от кода.
- **Увеличение объёма контекста запроса из-за одновременного учёта профиля, RAG и памяти.** Совместное включение профиля автора, RAG-контекста и подтверждённой памяти в одну итоговую инструкцию (раздел 4.8) увеличивает объём передаваемого модели контекста, что может влиять на стоимость, время отклика и ограничения конкретных моделей по длине контекста.
- **Ограничения Telegram как единственного канала для сложных форм ввода.** Пошаговый мастер создания профиля, выбор типа контента/Skill/модели и ввод исходных данных Skill реализуются средствами Telegram-интерфейса (кнопки, пошаговые сообщения); сложность части сценариев (раздел 3) может упираться в ограничения Telegram Bot API по интерактивности форм.
- **Риск неограниченного понимания термина «генерация контента».** Без строгого соблюдения зафиксированного перечня модальностей и типов контента (раздел 4.4, раздел 9, пункт 1) термин может трактоваться расширительно на этапе реализации; документ ограничивает MVP модальностями TEXT и IMAGE и явно исключает видео и аудио (раздел 7).
- **Специфические риски генерации изображений.** Модальность IMAGE впервые включена в состав MVP (раздел 4.4): соответствие результата ожиданиям пользователя менее предсказуемо, чем для текста, а конкретный выбор модели/API генерации изображений и необходимость модерации содержимого остаются вопросом системной архитектуры и конфигурации каталога моделей, а не анализа требований.
- **Сохранение единственного хранилища структурированных данных — только при текущих допущениях по нагрузке.** Расширение состава сущностей (несколько профилей на пользователя, каталог Skills, каталог моделей) увеличивает число записей и операций чтения/записи; при превышении принятых допущений по нагрузке (раздел 5) потребуется пересмотр выбора СУБД.
- **Отсутствие автоматического fallback между моделями.** Осознанно принятое ограничение MVP (раздел 4.7): недоступность выбранной или автоматически подобранной модели приводит к отказу в обработке конкретного запроса до повторного выбора пользователем, без автоматического перехода на резервную модель.
- **Зависимость от внешних поставщиков моделей и, при использовании единого шлюза доступа к моделям, от его доступности.** Единый абстрактный слой доступа к моделям (раздел 8, раздел 9, пункт 6) снижает число прямых интеграций, но, если системная архитектура реализует его через общий шлюз, добавляет зависимость от доступности этого шлюза как дополнительного внешнего звена между системой и поставщиками моделей.
